# SIS — Novonordisk Supply Chain (chore/remake)

Laravel 10 + Inertia 2 + **Svelte 5 (runes)** + **Metronic 9 (Tailwind 4, built from source)**. This file is the source of truth for a fresh session — read it first.

## Architecture
- **Decoupled JSON API + thin Inertia shell.** Controllers return the envelope `{ status, message, data }` (paginated `data = { data, meta, links }`); pages are Svelte and fetch client-side via the shared API client (NOT `Inertia::render` for data — web routes only render page shells, and they do it through `App\Http\Controllers\Web\*`, never inline in `routes/web.php`).
- Query contract (spatie/query-builder): `filter[field]`, `filter[search]`, `sort=field|-field`, `include=rel`, `per_page`, `page`.
- **No soft deletes, no archive.** `destroy` is a real delete; there are no restore/force-delete routes, no `deleted_at`, no `filter[trashed]`. Don't reintroduce them — and never add `Rule::unique(...)->whereNull('deleted_at')`, which is what broke every create/update the moment the column went.
- Auth: custom Sanctum-session + Azure SSO, approval gate via **`App\States\User\UserStatus`** (spatie/model-states): `pending` → `verified`|`approved`|`rejected`; `verified` → `approved`|`rejected`; `approved` → `rejected`; `rejected` → `approved` (nothing ever returns to `pending`). **Only `approved` may sign in** — gate on `$user->canLogin()`, never on the raw status. Azure SSO self-signup lands on `verified` (it proves identity, not admission); an admin-created user starts `approved` (creating it *is* the approval). Transitions are `POST users/{user}/{approve,reject,verify}`, each permission-gated; a disallowed transition is a 422, not a 500. Frontend labels/variants live in `lib/user.js`. Single upload route `POST /api/v1/admin/uploads` → forms submit only the returned media `id`. **Everything lives under the `admin` prefix** — only admins can reach this system — including auth (`/api/v1/admin/auth/*`), which stays *outside* `verify.auth` or you could never log in.
- **Sessions = Laravel's table in our shape.** `SESSION_DRIVER=database`; `App\Services\Sessions\SessionHandler` extends Laravel's and translates on the way in/out — `id` is a ULID (PHP's session id lives in `session_id`), `last_activity` is a datetime (Laravel writes unix seconds), plus `created_at`/`updated_at`. Registered over the `database` driver in `AppServiceProvider::useOurSessionTable()`. **`session_id` is the cookie value — a credential, never exposed**: it is in the model's `$hidden` and absent from `SessionData`; routes bind on the ULID. **Sessions are NOT audited** — the table already records who was signed in from where, and a session is written on *every request*, so an observer would add a row per page view. Deleting a row IS the logout. **`user_id` MUST stay nullable** — Laravel writes a session for guests too (the login page needs one for its CSRF token); NOT NULL makes the insert fail, the handler swallows it, and *nobody can log in*. A session is INSERTed on first contact and UPDATEd every request after; login calls `regenerate(true)` so the pre-login guest row is destroyed rather than orphaned. Expired rows: Laravel's `gc()` only fires on a `session.lottery` roll (2% of requests), so `Session` is `Prunable` and `model:prune` runs daily; reads go through `scopeActive()`/`scopeExpired()` rather than trusting the table. **Sessions are read per-user only** — one `SessionsController` (`GET sessions/{user}`, `DELETE sessions/{session}`), no app-wide list; plus `POST users/{user}/logout-devices`, which iterates because a builder `->delete()` fires no events.
- **Uploads = our own `App\Models\Media`** (spatie/laravel-medialibrary was removed — we used ~5% of it and fought the rest). `config/uploads.php`; `UploadService` is the only way files enter/move/leave. Two stages: `quarantine` disk → `ScanUpload` job (`FILE_SCANNER=null|clamav`, state `pending→clean|infected|failed`) → `public` disk. **Storage is flat**: every file is `uploads/{ULID}.{ext}` — the owner + collection live in the DB only (`model_type`/`model_id` nullable, `collection_name`), so attach/detach are pure DB writes and a file never moves. `media.name` = the real filename for display, `file_name` = the generated unique one. A file belongs to one model at a time; attaching an owned file copies it. `HasMedia` trait (`App\Traits\Uploads`) gives `media()`/`getMedia()`/`getFirstMediaUrl()`/`singleFileCollections()`.
- **Pruning is `Prunable` + `model:prune` (daily), never a bespoke command.** `Session` prunes expired rows and `Notification` is `MassPrunable`. **`Media` is deliberately NOT prunable** — it used to sweep never-attached uploads after 30 days, which is unsafe now that editor-inserted images are free media by design: they live in a page's HTML but are owned by nothing, so the sweep would eventually delete a file a live page still renders. Nothing deletes a file automatically; `DELETE media/{media}` (`media.destroy`, free media only — an attached one is a 422) is the single exit, surfaced as a Delete action on the Media page. The library accumulates, and that is the intended trade.
- **Content images are free media, not a collection.** A content module owns exactly one `thumbnail` (plus `files` on Album). Images the editor uploads are inserted by URL and never attached to anything — there is no `images` array on any DTO, no `IMAGES_COLLECTION`, and no content-scanning. `UploadService::sync()` survives for Album's ordered `files` gallery only.
- **Activity log** (spatie/activitylog): written by observers only, never by hand. Every observer extends `App\Observers\BaseObserver` (one class, both modes) and is registered in `AppServiceProvider`. **Pivot changes log against their parent** (granting a permission to an ApiKey is an `attached` activity on the ApiKey) — a pivot observer opts in by overriding `isPivot()` to `true` and implementing `parent()`/`related()`; everything else logs its own model's lifecycle. Causer = User *or* ApiKey via `CauserResolver` in `AppServiceProvider` (honour its `$subject` arg — an explicit `causedBy()` must win). Secrets are stripped by `neverLog()` (global backstop) + `ignored()` (per-model noise). **A delete only keeps what `loggedOnDelete()` names** — the record itself is gone, so name the columns worth keeping; `neverLog()`/`ignored()` still win over it. Read-only `GET /api/v1/admin/activities`; note `filter[search]` only covers `description`/`event`/`log_name`, and `description` holds just the event slug — so a deleted record is findable by `subject_id`, not by name; polymorphic columns are exposed as `App\Enums\MorphType` aliases (`api_key`), never class names. The UI builds messages from `(log_name, event)` — see `lib/activity.js`; `description` is the stored English fallback.
- **The admin UI itself is English-only and hardcoded.** There is no `$t()`, no `lib/i18n`, no `i18n` Inertia prop, no locale switch, no RTL: `<html dir="ltr" lang="en">` is fixed in `app.blade.php`, and nothing calls `App::setLocale()`. Write admin UI strings as literals in the component. `HandleInertiaRequests` shares only `auth` + `media` (upload rules). Activity-log wording lives in `lib/activity.js` (`ACTIVITY_MESSAGES`/`EVENT_LABELS`/`LOG_NAME_LABELS`/`SUBJECT_TYPE_LABELS`) — not in `lang/`.
- **Localisation is a managed catalogue, not a UI layer.** `lang/` holds 9 locales (`en ar fr es de it pt ru hi`), each with a full `validation.php` (Laravel's own server-side messages, e.g. `__('validation.date')` in `ActivitiesController`) plus the catalogue groups an admin edits. **Translated strings live in the PHP files, never in the database** — `translation_keys` is a read-only key registry (`group` + dotted `key`), and the Translations page paginates *that* while reading each value out of `lang/{code}/{group}.php`. `App\Services\Translations\TranslationService` is the only thing that touches those files: `put()` is parse → verify → replace under a sidecar `flock` (every registered key must survive the write), then a temp-file `rename()` and `opcache_invalidate()` — **that OPcache call is the whole cache story; Laravel has no lang cache and this app has no `Cache::` usage, so never add a `cache:clear` here.** A `Language` row owns its folder via `LanguageObserver`: create makes it, a `code` change renames it, and **delete deliberately leaves it on disk** (the translations are source and outlive the row). Exactly one `is_default`, enforced by a builder update in `saved()`. `@lang('common.save')` resolves against these files.
- **`lang/` is GENERATED OUTPUT and gitignored; the tracked source is `config/translations.php` — ONE file, ~1,650 lines.** It holds the `groups` whitelist, the code/group patterns, `fill_missing_keys`, and `keys` — every group's catalogue nested under it, each entry a `locale => string` map covering all 9 codes. It was six files under `config/translations/` and is deliberately one: a nested config directory bought nothing but six files to open. Read it with a search, not by scrolling. `TranslationKeysSeeder` mirrors `(group, key)` into the registry and writes each locale's file from that map. Adding a line is: add it here, reseed. Reseeding is `onlyMissing` by default so it never clobbers an admin's edit — set `TRANSLATIONS_OVERWRITE=true` to push an edited config string onto an install that already has the file. **`fill_missing_keys` is `false`**: Laravel falls back to `fallback_locale` only when a key is ABSENT, never when it is `''`, so filling would render blank headings to public visitors instead of English.
- **ANY STRING A VISITOR READS IS A LANG KEY, NEVER A SETTING.** A settings row holds one value for every locale, so the Arabic site would show the English text — which is why the site title, tagline, meta description and keywords live in the `common` group and `general.site_name` / `general.tagline` / the whole `seo` settings group were removed. `SiteContext::name()` is `__('common.site_title')`.
- **`config/settings.php` is SEVEN settings in three groups, and adding an eighth needs a reason.** `code.{head,foot,support_button}` (raw markup, stored XSS by design — keep the group off untrusted roles), `homepage.{banner_mode,pathway_program}`, `integrations.{analytics,ai}`. Anything a visitor reads is a lang key; anything with one right answer is a constant (page size is `SiteController::PER_PAGE`, the logos are bundled files); and the menus resolve by `code` — `$site->menuItems('footer_primary')` — because a system menu's code is frozen and so already IS the stable reference a setting was trying to provide. `Integration::activeFor($type)` now consults `integrations.{type}` first and falls back to the oldest enabled one, which is what makes a single configured integration work with nothing chosen.
- **The two logo marks are bundled files, not settings.** `SiteContext::logo()` is `complete-logo.png` — crest plus wordmark, made for the header and unreadable small. `SiteContext::mark()` is `logo.png`, the crest alone, used by the footer, the section dividers and `og:image`. There is one school and one set of marks; making them configurable only let a fresh install render no logo at all.
- **DB-backed translations were considered and rejected — don't reopen it without the trigger below.** Files win here because `@lang()`/`__()` read them natively: a DB translator needs a loader override *and* a cache (every rendered string would otherwise be a query), and this app has no caching layer to put it in. The costs are already paid (lock, atomic rename, OPcache). **The one thing that flips the decision is a second app server** — file writes land on one node only, so the day this runs behind a load balancer or in more than one container, it must move to the DB. That swap is contained to `TranslationService::load()`/`put()`; nothing else touches the files. Secondary limit: you cannot sort or filter by translated *value* in SQL (hence `value` is absent from `allowedSorts`), so a "missing translations" filter costs a PHP-side scan over the whole registry rather than a `WHERE`.

## Frontend layout — `resources/` is TWO apps, split at the top level
```
resources/
├── admin/   css/{app,brand}.css · js/{app.js,bootstrap.js,Pages,components,layouts,lib}
│            views/app.blade.php · metronic/ (the licensed theme source — gitignored, see below)
└── site/    css/{site,forms}.css + css/site/{tokens,fonts,icons,base,components,sections}.css
             js/{site.js, site/*, components/forms, lib/forms}
             views/{layout, partials, pages, forms, sitemap}
```
- **The public site is server-rendered Blade with an OPTIONAL locale prefix, and its absence is NEVER a redirect.** `routes/web.php` defines the site routes once in a `$site` closure and registers it TWICE: `prefix('{locale}')->name('web.site.')` first, then unprefixed as `web.site.root.`. So `/contact` serves the default language directly and `/ar/contact` serves Arabic — nothing bounces, and a shared link opens the page it names. **Do NOT collapse that to one group with `prefix('{locale?}')`** — Laravel compiles an optional parameter as a trailing-optional segment, so inside a prefix it stays effectively required and every unprefixed URL 404s. The form routes keep their existing `/forms/{locale}/{slug}` URIs and were NOT moved.
- **Three things make the optional prefix work, and removing any one breaks the site quietly.** (1) `Route::pattern('locale', '[a-z]{2}')` in `RouteServiceProvider::boot()` BEFORE `$this->routes()` — without it `{locale}` swallows any single segment, so `/articles` is read as the locale `articles` and every unprefixed page 404s; and a pattern registered after is missing from a `route:cache` build entirely. (2) `SetLocale` filling in `Language::defaultCode()` when the segment is absent, narrowing to the ENABLED codes (404 otherwise), and setting the Carbon locale. (3) `URL::defaults(['locale' => …])` for EVERY locale INCLUDING the default — a site route cannot be BUILT without a value, so skipping it 500s every default-language page with "Missing required parameter". Keeping `/en` out of the generated URL is a separate, later job: `SiteServiceProvider::hideDefaultLocaleFromUrls()` strips it in `UrlGenerator::format()`.
- **`SiteServiceProvider::hideDefaultLocaleFromUrls()` is what makes the double registration coherent.** A `URL::formatPathUsing` hook strips a leading `/{default}` from every generated path, so the canonical, the hreflang set, the sitemap and every link all say `/contact` while `route(…, ['locale' => 'ar'])` still says `/ar/contact`. Without it a visitor reading `/contact` would click a menu built by `route()` and be thrown back into `/en/…`. It only ever strips a whole first segment, so `/admin/…` and `/forms/en/…` are untouched, and `asset()` does not pass through `format()` at all. `/en/contact` survives as an alias whose canonical points at `/contact`, which is what stops the two being duplicate content. **Site controllers therefore take no `$locale` argument** — the unprefixed routes have no such parameter; read `$this->site()->locale`. `Seo::alternates()` maps a `web.site.root.*` name back to its prefixed twin, and the language switcher reads that same map so it and the hreflang tags cannot disagree.
- **Cost of registering the prefixed group first:** a Page whose slug is exactly two lowercase letters is unreachable unprefixed — `/hr` is read as a locale, fails the enabled-codes check and 404s. It is still reachable at `/en/hr`.
- **`app/Services/Site/` is ONE class — `SiteContext` — and it holds the GLOBAL half of a request only.** Chrome, languages, settings, menus: things every page needs and no page owns. Its whole public surface is getters — `language()` (which is where `locale()`, `direction()` and `isRtl()` all come from, because a Language row already carries the code and `is_rtl`), `languages()`, `defaultLanguage()`, `setting()`, `menuItems()`, `contacts()`, `analytics()`, `url()` — plus the `LINK_ROUTES` map. Nothing else may go back in: **a page's own data belongs to its controller**.
- **THE SEO BUILDER IS GONE FROM `SiteContext`, and putting one back is the mistake this shape exists to prevent.** `seo()`, `meta()`, `breadcrumbs()`, `structuredData()`, `canonical()`, `alternates()` and a private `translated()` reader all lived on it, which meant answering "what does this page put in its `<title>`?" started in a controller, passed through a MUTABLE builder on a singleton, and finished in a partial — three files for one question, and a view (`pages/error`, `forms/*`) could mutate it after the layout had begun. Each controller now assembles a plain `$seo` array and a plain `$breadcrumbs` array and hands both to `view()`. **One method to read per page.** The array's keys are documented on `Web\Site\SiteController`; `site::layout` is the only reader.
- **What is the SAME on every page lives in the LAYOUT, not in twenty controllers:** the ` — Saud International Schools` title suffix (skipped when the title already IS the site name), `strip_tags` + 160-char trim on the description, the crest as the `og:image` fallback, and `x-default`. A controller states its page's own title, description, image, canonical, robots, type and alternates — and nothing about how they are dressed.
- **No JSON-LD.** `structuredData()`, the `EducationalOrganization` node and the `BreadcrumbList` graph were removed with the builder; `partials/breadcrumb` reads the controller's `$breadcrumbs` directly and prepends Home itself, so no controller can forget it or spell it differently. `GET /sitemap.xml` is one document with `xhtml:link` alternates; `GET /robots.txt` is a ROUTE and `public/robots.txt` was deleted, because the web server serves `public/` first and would have made the route dead code. The sitemap owns its own `SLUG_ROUTES` map (system page slug → the fixed route that renders it) because it is the only thing that needs one.
- **Site views get ONE ambient variable, `$site`**, from a closure composer on `site::*` in `App\Providers\SiteServiceProvider`. NO global helper. Registering it as a container singleton IS the per-request memoisation — no static state, no `Cache::` layer. It lazily loads settings (one query for the catalogue) and contact details (one query). **Menus are addressed BY CODE — `menuItems('footer_primary')` — with no slot map in between**, one query per menu, memoised by code, whole two-level tree eager-loaded; a page pays only for the menus it renders, so the seeded-but-unused `footer_secondary` is never loaded. Items come back with **`$item->url` ALREADY RESOLVED** — the linked morph wins over the typed external `url`, and null means render an unlinked label. There is no `menuUrl()` to call afterwards, and an unknown code returns an empty collection. `url()` survives as the one morph→route resolver (banners and `$page->menu` use it) and returns null rather than throwing: a menu is chrome and must never 500 a page.
- **The name, the marks and the placeholder are written out where they are used**, not read off `$site`: `@lang('common.site_title')`, `asset('assets/site/images/logo-full.png')` (header), `logo-mark.png` (footer, dividers, og:image), `favicon.png`, `placeholder.png`. One school, one set of marks — a getter that returns a constant is a getter that hides one.
- **Settings expose ONE method, `setting($path)`, returning the stored value.** `settingModel()`/`settingModels()` are gone: a `model` setting stores a bare id and the caller loads what it wants (`Program::find($site->setting('homepage.pathway_program'))`), which is clearer than a generic resolver that had to read `config/settings.php` to work out the class first.
- **The public 404 is `site::pages.error`, deliberately NOT in an `errors/` directory.** Laravel's `RegisterErrorViewPaths` maps every `config('view.paths')` entry plus `/errors` into the `errors` namespace, so a file there answers `errors::404` for the ADMIN and the API too with no way to opt out. `App\Exceptions\Handler::renderHttpException()` renders it by name for site requests only; `admin/*` and `api/*` keep Laravel's own page.
- **The public site is a PORT, not a redesign — match `old/` unless there is a reason not to.** Two rules the home page exists to demonstrate: SECTION HEADINGS RENDER UNCONDITIONALLY (only the content inside a section is `@if`-ed, so an empty news list still says "Latest news" and still offers its CTA rather than the section vanishing), and the home page carries NO article-style body block — the `home` Page row supplies the title and meta description through `$seo` and nothing else. Hero is a swiper of banners with video support and a `btn btn-on-dark` CTA (transparent, white border, fills on hover); a solid `.btn` on hero artwork reads as a foreign object.
- **`site/forms-theme.css` repaints the form renderer in the site's design language** — the `.input` border and focus ring, the `.btn` gradient sweep, brand `#2a5d91` instead of Metronic's `#1b84ff`, and `--sisf-font: inherit` so RTL picks up DINNext. `forms.css` keeps neutral token-free defaults because the same component renders in the admin builder preview, which never loads this file. **BOTH SHEETS MUST STAY UNLAYERED.** An unlayered rule beats a layered one whatever the specificity, so wrapping the theme in `@layer components` (the first attempt) let it win only where `forms.css` declared nothing — the title hid and every control kept its Metronic look. Also note a button element is `.sisf-el--button > .sisf-control > button`: `justify-content` on the outer row computes fine and does nothing, because its single child already fills it.
- **The rendered phone field gets intl-tel-input from `site/forms.js`, not from the component.** `PhoneControl` renders a bare `<input type="tel">` on purpose — it also runs in the admin preview, where ~90 kB of country metadata is dead weight. The site already pays that cost for its own Blade phone fields, so `attachPhoneWidget()` adds the selector after mount and re-dispatches `input` on `countrychange` (picking a country rewrites the value without firing one). `components.css` already targets `.iti input.iti__tel-input`, a class the plugin adds itself, so the control inherits the site's existing phone treatment for free. Enhancement only: with the plugin blocked the field still works, and `PhoneType::store()` normalises to E164 server-side regardless.
- **ONE php-directive form per Blade file — never both the inline and the block form.** Blade's `storePhpBlocks` matches the opening directive through the first closing one across the WHOLE file, and it runs BEFORE comments are stripped. An inline directive above a block one pairs with the BLOCK's terminator and swallows everything between, compiling to a syntax error pointing at an unrelated later line — and writing the directives literally inside a Blade comment is enough to trigger it on its own. `partials/{pagination,media-list}.blade.php` carry the note.
- **The admin is the Inertia+Svelte+Metronic app. The site is the public website end users visit.** Nothing under `site/` may import from `admin/`, or the whole Metronic theme lands on a public page. The two have no shared module: the form renderer under `site/js/components/forms` is site-only, and the admin builder keeps its own copies of the two helpers it needs (`admin/js/lib/forms/{values,i18n}.js`) rather than reaching across.
- **Aliases:** `@` → `resources/admin/js` (so every existing admin import is untouched), `@site` → `resources/site/js`. An `@site/` import inside `resources/admin` is a boundary violation you can grep for.
- **Separate builds, separate manifests.** `npm run build` = `build:admin` then `build:site`; each is `vite build --mode {admin,site}` and writes to `public/build/{admin,site}`. A Vite build emits exactly one `manifest.json`, so the two cannot share a directory — hence the second argument in `@vite([...], 'build/admin')` / `@vite([...], 'build/site')`. A bare `vite build` with no `--mode` throws rather than silently half-building. `npm run dev` still serves BOTH from one server (Laravel keys hot mode off a single `public/hot` and ignores the build directory while it exists, so two dev servers cannot coexist).
- **Blade is namespaced `admin::` / `site::`** (`AppServiceProvider::registerViewNamespaces()`, both paths also in `config/view.php`). Inertia's `$rootView` is `admin::app`; the public form pages are `site::forms.*`. Use the prefix in our own code so a name that exists on both sides can never resolve to the wrong half.
- **Tailwind: both stylesheets use `@import 'tailwindcss' source(none)` + explicit `@source`.** v4's automatic source detection scans the WHOLE project and ignores `@source`, so without this the public page compiled every utility class found in `resources/admin` (site CSS was 37 kB; it is 11 kB scoped). Each side scans `../js/**/*.{svelte,js}` **and `../views/**/*.blade.php`** — the Blade shell's `<body>` class list is Tailwind utilities too, and dropping that glob strips the demo1 layout off the page.
- **`public/` mirrors the split:** `public/assets/admin/media/**` (Metronic's app/audio/avatars/brand-logos/flags/images) and `public/assets/site/` for the site's own static files. `public/build/` is Vite output, gitignored.
- Admin `lib/` — `api/{client,useIndex.svelte,useForm.svelte}`, `date`, `format`, `permissions`, `upload`, `activity`, `kt` (KTUI init), `menu` (sidebar config), `portal`, `toast`, `confirm`.
- Admin `components/{ui,form,data,media,feedback,layout,activity,charts,forms-builder}` — the deduplicated kit. Key: `IndexCard` (Metronic list card + fly-in create/edit swap), `DataTable` (sortable, skeleton, `kt-table`), `Filters` (config-driven drawer incl. `resource-select`), `Drawer`/`Modal` (Svelte-driven, portaled), `Dropdown` (portaled — avoids table overflow clipping), `Select` (async combobox = Select2 replacement), `PhoneInput` (intl-tel-input), `PasswordInput`, `DatePicker` (flatpickr), `MediaPicker`/`MediaLibraryModal`.
- Admin `layouts/{AdminLayout,AuthLayout}`, `Pages/Admin/**` (the `Admin/` segment is kept: it is the Inertia page key that `inertia('Admin/Users/Index')` passes) + `Pages/Admin/Auth/Login`.
- Note `components/form/` (admin input kit) and `site/js/components/forms/` (public renderer) are different things — before the split they sat side by side, distinguished only by a plural `s`.

## Conventions (match these)
- **Svelte 5 runes only** — `$props/$state/$derived/$effect`, callback props, snippets. No `export let`/`createEventDispatcher`/`on:`.
- Preserve the **Metronic demo1 look** (`kt-*` classes). Icons = **keenicons** (`ki-filled ki-*`).
- A module Index = `AdminLayout` + `IndexCard` with `toolbar`/`form`/`table` snippets; create/edit = **fly-in card swap**; view/filters/pivots = **right-side drawers**; row actions = portaled `Dropdown`.
- UI strings are plain English literals in the component — no translation layer, no lang files.
- **Phone inputs are normalized before validation.** A Data class with phone fields does `use App\Traits\Data\NormalizesPhones;` and names them in `phoneFields()` (defaults to `['phone']`). It hooks spatie/laravel-data's `prepareForPipeline()`, which runs BEFORE every pipe — so `Rule::unique` and `App\Rules\PhoneNumber` see E164 (`+213555123456`) and `+213 555 123 456` collides with an existing row instead of becoming a second account. `App\Services\Phone\PhoneFormatter::e164()` is the one formatter; it returns null for anything unparseable, and the trait falls back to the raw input so the validator reports it rather than `nullable` silently storing no phone.
- **Models are banner-sectioned** — every model in `app/Models/` has exactly four numbered sections, always all four in this order even when empty: `1. Attributes` (consts, `$guarded`, `$hidden`, `$appends`, `$casts`) → `2. Relationships` → `3. Accessors` (`get*Attribute()`) → `4. Methods` (everything else). Don't invent domain sections (Lifecycle, Permissions, …) — fold them into these. Format:
  ```php
      /* -----------------------------------------
       1. Attributes
      ------------------------------------------*/
  ```

## Gotchas (already solved — don't reintroduce)
- npm `@keenthemes/ktui` has **no `KTMenu`** → sidebar accordion/collapse are **Svelte-driven**, not `data-kt-menu`. KTUI (dropdowns/toggle/sticky/theme-switch) is init via `lib/kt.js` `initKt()` in `app.js` + `AdminLayout`.
- **Keenicons** must be imported in `app.js` (unlayered), NOT `@import`-ed into `app.css`, or Tailwind's `::before` reset wipes the glyphs.
- Don't put `kt-drawer` on the Svelte `Drawer` (its base CSS mis-positions it). `#app` needs `flex-grow:1;width:100%` (in `app.css`).
- KTUI widgets in client-rendered content (form panels, drawers) won't be re-init'd → use Svelte-native equivalents (`PasswordInput`, portaled `Dropdown`).
- **Flat media storage: never delete a media's *directory*, only its file.** The folder is shared by every model — a `deleteDirectory()` there wipes the whole app (this is what medialibrary's `DefaultFileRemover` and the old `ScanUpload` both did). Same reason `file_name` is a ULID with a unique index: two `invoice.pdf`s would otherwise be the same file.
- **Observers write the audit log; don't call `activity()` from controllers.** A model `updated` diff must ignore timestamps and skip empty diffs, or every password change writes a meaningless row.
- `useIndex` reads its `filter` **once at init** → a drawer reused across rows needs `setFilters()` on open (and `readUrl:false`, or it fights the page's query string).
- `Filters` passes `value=` (not `bind:value`) to `Select` and relies on `onchange`. A `resource-select` may take function props of the draft + `dependsOn` (see the causer filter in `Pages/Admin/Activities/Index.svelte`).
- PHP here is **8.1** — no constants in traits, no `readonly` classes.

- **The site has NO seeded content in production, by design.** `PagesSeeder` ships the 14 system pages (slugs the controllers resolve — renaming one 404s a page, which is what `is_system` prevents), `MenusSeeder` the 4 menus and **nothing in them**, `config/forms.php` the `contact` and `inquiries` system forms. `DemoContentSeeder` fills in articles, programmes, contact details and menu items so a dev checkout is legible — it runs from the `local` branch of `DatabaseSeeder` ONLY, is `firstOrCreate` throughout, and is a fixture rather than a second opinion about what the site should contain. Articles, albums, events, achievements, programmes, brands, banners, partners and every menu item are empty: each listing renders its empty state until an admin adds rows. **Page titles and form copy ARE seeded in all 9 locales** — those are the strings the app itself resolves, and a system page with no title in the active language renders a blank heading. The system forms carry catalogue KEYS (`label_key`, `title_key`, `confirmation_key`) that `FormsSeeder` resolves per locale, so the wording has one home rather than two that drift.
- **Site controllers extend `Web\Site\SiteController`, which is DELIBERATELY ALMOST EMPTY** — `site()` and a `PER_PAGE` constant, nothing else. It used to carry `page()`, `optionalPage()`, `locale()`, `slug()`, `perPage()`, `seo()`, `trail()` and `t()`: seven wrappers that each hid one line and, between them, meant reading a page's controller told you almost nothing about what the page renders. Every method now spells out its own query, `$seo` and `$breadcrumbs` in full. The `<head>` contract is documented on the base class's docblock.
- **NEVER take a route segment as a controller method argument on a site route.** Laravel resolves non-class controller parameters POSITIONALLY from the route's parameter list, not by matching their names — so on `/{locale}/articles/{slug}` a `show(string $slug)` is handed the LOCALE and every detail page 404s hunting an article slugged `en`. The unprefixed twin has one parameter and works fine, which makes the bug look locale-specific when it is not. Use `$this->slug()`, which reads it by name and is correct whichever of the two routes matched.
- **`partials/page-hero` falls back to the bundled `placeholder.png`.** Every hero is a full-viewport image behind a dark scrim, so a null thumbnail leaves a bare gradient with the title floating on it — that reads as a broken image, not as a design. The 404 page is built the same way as every other page (hero, breadcrumb, body) for the same reason: dropping the chrome makes a wrong address look like a server fault. Its `error` Page row is seeded with a title in all 9 locales; the body falls back to the `site.error.*` keys rather than being seeded too, so there is one copy of that wording, not two.
- **`site::pages.error` is the ONE view that builds its own `$seo`**, because it has no controller — `App\Exceptions\Handler` renders it knowing only that something 404'd. Its `alternates` are deliberately empty (a wrong address has no translations to offer; the drawer's switcher already falls back to each locale's home) and every read is null-safe, because anything that throws in there turns a 404 into a 500 with no useful trace.
- **`resources/site/views/components/` is gone.** `<x-site::panel>` and `<x-site::field>` were an anonymous-component namespace holding a collapsible card and a form row; `field` had no callers and `panel` had five, so its markup is written out at each one. Note the old component never rendered `$attributes`, so the `class="mb-4"` that `guidelines` and `brands/show` passed it was silently dropped — the inlined copies keep those cards stacking flush, which is what the site has always shown.
- **No automated tests:** `pdo_sqlite` is not enabled in this PHP, and `phpunit.xml` still points at the real dev DB — a `RefreshDatabase` test would wipe it. Enable `extension=pdo_sqlite` + uncomment the sqlite lines in `phpunit.xml` before adding tests.
- **Deferred:** the ~26 orphaned domain modules (Products, PurchaseOrders, Warehouse, …) were deleted (recoverable from git) — rebuild on this same standard when their backends exist.
- **Inert on purpose:** the job-application wizard (`/{locale}/jobs/apply`) and the visit-booking island. Both ship as front-end files with all nine locales of copy in `config/translations/{jobs,visits}.php`, and neither has a model, a POST route or a backend — `JobsController::apply()` renders noindex and nothing links to it, and the visit island is registered in `site/islands.js` but mounted by no page. Standing either up is a backend plus routes, not a translation project.

## Build / run
`npm run build` (both bundles; or `npm run build:admin` / `npm run build:site`, or `npm run dev` for one server serving both) + `php artisan serve`. No jQuery. Detailed history + rationale: `~/.claude/plans/audit-the-app-folder-elegant-wreath.md` and the `remake-context-artifacts` memory.

**Metronic source is `resources/admin/metronic/`** (5,275 files, ~547 MB) — it belongs to the admin because nothing else may use it. Gitignored via `/resources/admin/metronic`; if you ever move it again, move that `.gitignore` line in the SAME commit or a licensed third-party theme lands in the repo. Only four imports reference it: three `@import '../metronic/src/css/…'` in `admin/css/app.css` and the keenicons `styles.bundle.css` in `admin/js/app.js`. It is deliberately NOT covered by the `@source` globs, so Tailwind never scans the theme's own 5,275 files. Because it sits inside `resources/`, a raw `grep -r resources/` in a shell walks all of them and effectively hangs — pass `--exclude-dir=metronic`. The Grep tool is unaffected (ripgrep honours `.gitignore`).
