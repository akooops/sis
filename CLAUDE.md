# SIS — Novonordisk Supply Chain (chore/remake)

Laravel 10 + Inertia 2 + **Svelte 5 (runes)** + **Metronic 9 (Tailwind 4, built from source)**. This file is the source of truth for a fresh session — read it first.

## Architecture
- **Decoupled JSON API + thin Inertia shell.** Controllers return the envelope `{ status, message, data }` (paginated `data = { data, meta, links }`); pages are Svelte and fetch client-side via the shared API client (NOT `Inertia::render` for data — web routes only render page shells, and they do it through `App\Http\Controllers\Web\*`, never inline in `routes/web.php`).
- Query contract (spatie/query-builder): `filter[field]`, `filter[search]`, `sort=field|-field`, `include=rel`, `per_page`, `page`.
- **No soft deletes, no archive.** `destroy` is a real delete; there are no restore/force-delete routes, no `deleted_at`, no `filter[trashed]`. Don't reintroduce them — and never add `Rule::unique(...)->whereNull('deleted_at')`, which is what broke every create/update the moment the column went.
- Auth: custom Sanctum-session + Azure SSO, approval gate via **`App\States\User\UserStatus`** (spatie/model-states): `pending` → `verified`|`approved`|`rejected`; `verified` → `approved`|`rejected`; `approved` → `rejected`; `rejected` → `approved` (nothing ever returns to `pending`). **Only `approved` may sign in** — gate on `$user->canLogin()`, never on the raw status. Azure SSO self-signup lands on `verified` (it proves identity, not admission); an admin-created user starts `approved` (creating it *is* the approval). Transitions are `POST users/{user}/{approve,reject,verify}`, each permission-gated; a disallowed transition is a 422, not a 500. Frontend labels/variants live in `lib/user.js`. Single upload route `POST /api/v1/admin/uploads` → forms submit only the returned media `id`. **Everything lives under the `admin` prefix** — only admins can reach this system — including auth (`/api/v1/admin/auth/*`), which stays *outside* `verify.auth` or you could never log in.
- **Sessions = Laravel's table in our shape.** `SESSION_DRIVER=database`; `App\Services\Sessions\SessionHandler` extends Laravel's and translates on the way in/out — `id` is a ULID (PHP's session id lives in `session_id`), `last_activity` is a datetime (Laravel writes unix seconds), plus `created_at`/`updated_at`. Registered over the `database` driver in `AppServiceProvider::useOurSessionTable()`. **`session_id` is the cookie value — a credential, never exposed**: it is in the model's `$hidden` and absent from `SessionData`; routes bind on the ULID. **Sessions are NOT audited** — the table already records who was signed in from where, and a session is written on *every request*, so an observer would add a row per page view. Deleting a row IS the logout. **`user_id` MUST stay nullable** — Laravel writes a session for guests too (the login page needs one for its CSRF token); NOT NULL makes the insert fail, the handler swallows it, and *nobody can log in*. A session is INSERTed on first contact and UPDATEd every request after; login calls `regenerate(true)` so the pre-login guest row is destroyed rather than orphaned. Expired rows: Laravel's `gc()` only fires on a `session.lottery` roll (2% of requests), so `Session` is `Prunable` and `model:prune` runs daily; reads go through `scopeActive()`/`scopeExpired()` rather than trusting the table. **Sessions are read per-user only** — one `SessionsController` (`GET sessions/{user}`, `DELETE sessions/{session}`), no app-wide list; plus `POST users/{user}/logout-devices`, which iterates because a builder `->delete()` fires no events.
- **Uploads = our own `App\Models\Media`** (spatie/laravel-medialibrary was removed — we used ~5% of it and fought the rest). `config/uploads.php`; `UploadService` is the only way files enter/move/leave. Two stages: `quarantine` disk → `ScanUpload` job (`FILE_SCANNER=null|clamav`, state `pending→clean|infected|failed`) → `public` disk. **Storage is flat**: every file is `uploads/{ULID}.{ext}` — the owner + collection live in the DB only (`model_type`/`model_id` nullable, `collection_name`), so attach/detach are pure DB writes and a file never moves. `media.name` = the real filename for display, `file_name` = the generated unique one. A file belongs to one model at a time; attaching an owned file copies it. `HasMedia` trait (`App\Traits\Uploads`) gives `media()`/`getMedia()`/`getFirstMediaUrl()`/`singleFileCollections()`.
- **Pruning is `Prunable` + `model:prune` (daily), never a bespoke command.** `Session` prunes expired rows and `Notification` is `MassPrunable`. **`Media` is deliberately NOT prunable** — it used to sweep never-attached uploads after 30 days, which is unsafe now that editor-inserted images are free media by design: they live in a page's HTML but are owned by nothing, so the sweep would eventually delete a file a live page still renders. Nothing deletes a file automatically; `DELETE media/{media}` (`media.destroy`, free media only — an attached one is a 422) is the single exit, surfaced as a Delete action on the Media page. The library accumulates, and that is the intended trade.
- **Content images are free media, not a collection.** A content module owns exactly one `thumbnail` (plus `files` on Album). Images the editor uploads are inserted by URL and never attached to anything — there is no `images` array on any DTO, no `IMAGES_COLLECTION`, and no content-scanning. `UploadService::sync()` survives for Album's ordered `files` gallery only.
- **Activity log** (spatie/activitylog): written by observers only, never by hand. Every observer extends `App\Observers\BaseObserver` (one class, both modes) and is registered in `AppServiceProvider`. **Pivot changes log against their parent** (granting a permission to an ApiKey is an `attached` activity on the ApiKey) — a pivot observer opts in by overriding `isPivot()` to `true` and implementing `parent()`/`related()`; everything else logs its own model's lifecycle. Causer = User *or* ApiKey via `CauserResolver` in `AppServiceProvider` (honour its `$subject` arg — an explicit `causedBy()` must win). Secrets are stripped by `neverLog()` (global backstop) + `ignored()` (per-model noise). **A delete only keeps what `loggedOnDelete()` names** — the record itself is gone, so name the columns worth keeping; `neverLog()`/`ignored()` still win over it. Read-only `GET /api/v1/admin/activities`; note `filter[search]` only covers `description`/`event`/`log_name`, and `description` holds just the event slug — so a deleted record is findable by `subject_id`, not by name; polymorphic columns are exposed as `App\Enums\MorphType` aliases (`api_key`), never class names. The UI builds messages from `(log_name, event)` — see `lib/activity.js`; `description` is the stored English fallback.
- **The admin UI itself is English-only and hardcoded.** There is no `$t()`, no `lib/i18n`, no `i18n` Inertia prop, no locale switch, no RTL: `<html dir="ltr" lang="en">` is fixed in `app.blade.php`, and nothing calls `App::setLocale()`. Write admin UI strings as literals in the component. `HandleInertiaRequests` shares only `auth` + `media` (upload rules). Activity-log wording lives in `lib/activity.js` (`ACTIVITY_MESSAGES`/`EVENT_LABELS`/`LOG_NAME_LABELS`/`SUBJECT_TYPE_LABELS`) — not in `lang/`.
- **Localisation is a managed catalogue, not a UI layer.** `lang/` holds 9 locales (`en ar fr es de it pt ru hi`), each with a full `validation.php` (Laravel's own server-side messages, e.g. `__('validation.date')` in `ActivitiesController`) plus the catalogue groups an admin edits. **Translated strings live in the PHP files, never in the database** — `translation_keys` is a read-only key registry (`group` + dotted `key`), and the Translations page paginates *that* while reading each value out of `lang/{code}/{group}.php`. `App\Services\Translations\TranslationService` is the only thing that touches those files: `put()` is parse → verify → replace under a sidecar `flock` (every registered key must survive the write), then a temp-file `rename()` and `opcache_invalidate()` — **that OPcache call is the whole cache story; Laravel has no lang cache and this app has no `Cache::` usage, so never add a `cache:clear` here.** A `Language` row owns its folder via `LanguageObserver`: create makes it, a `code` change renames it, and **delete deliberately leaves it on disk** (the translations are source and outlive the row). Exactly one `is_default`, enforced by a builder update in `saved()`. `@lang('common.save')` resolves against these files.
- **`lang/` is GENERATED OUTPUT and gitignored; the tracked source is `TranslationKeysSeeder::catalogue()` — ONE method, ~1,700 lines.** Each entry is a `locale => string` map covering all 9 codes, nested under its group. **CONTENT LIVES IN THE SEEDER, SETTINGS LIVE IN CONFIG**: `config/translations.php` is now four entries — the `groups` whitelist, the code/group path patterns and `fill_missing_keys` — and nothing else, because the running app never read the catalogue (`__()`/`@lang()` read `lang/`, which the seeder writes) while `config:cache` was serialising all 1,700 lines into every request's bootstrap. It was six files under `config/translations/`, then one config file, now one method. Read it with a search, not by scrolling. The seeder mirrors `(group, key)` into the registry and writes each locale's file from that map. Adding a line is: add it to `catalogue()`, reseed. Reseeding is `onlyMissing` by default so it never clobbers an admin's edit — set `TRANSLATIONS_OVERWRITE=true` to push an edited string onto an install that already has the file. **`fill_missing_keys` is `false`**: Laravel falls back to `fallback_locale` only when a key is ABSENT, never when it is `''`, so filling would render blank headings to public visitors instead of English.
- **ANY STRING A VISITOR READS IS A LANG KEY, NEVER A SETTING.** A settings row holds one value for every locale, so the Arabic site would show the English text — which is why the site title, tagline, meta description and keywords live in the `common` group and `general.site_name` / `general.tagline` / the whole `seo` settings group were removed. `SiteContext::name()` is `__('common.site_title')`.
- **`config/settings.php` is SEVEN settings in three groups, and adding an eighth needs a reason.** `code.{head,foot,support_button}` (raw markup, stored XSS by design — keep the group off untrusted roles), `homepage.{banner_mode,pathway_program}`, `integrations.{analytics,ai}`. Anything a visitor reads is a lang key; anything with one right answer is a constant (page size is `SiteController::PER_PAGE`, the logos are bundled files); and the menus resolve by `code` — `$site->menuItems('footer_primary')` — because a system menu's code is frozen and so already IS the stable reference a setting was trying to provide. `Integration::activeFor($type)` now consults `integrations.{type}` first and falls back to the oldest enabled one, which is what makes a single configured integration work with nothing chosen.
- **The two logo marks are bundled files, not settings.** `SiteContext::logo()` is `complete-logo.png` — crest plus wordmark, made for the header and unreadable small. `SiteContext::mark()` is `logo.png`, the crest alone, used by the footer, the section dividers and `og:image`. There is one school and one set of marks; making them configurable only let a fresh install render no logo at all.
- **DB-backed translations were considered and rejected — don't reopen it without the trigger below.** Files win here because `@lang()`/`__()` read them natively: a DB translator needs a loader override *and* a cache (every rendered string would otherwise be a query), and this app has no caching layer to put it in. The costs are already paid (lock, atomic rename, OPcache). **The one thing that flips the decision is a second app server** — file writes land on one node only, so the day this runs behind a load balancer or in more than one container, it must move to the DB. That swap is contained to `TranslationService::load()`/`put()`; nothing else touches the files. Secondary limit: you cannot sort or filter by translated *value* in SQL (hence `value` is absent from `allowedSorts`), so a "missing translations" filter costs a PHP-side scan over the whole registry rather than a `WHERE`.

## Frontend layout — `resources/` is TWO apps, split at the top level
```
resources/
├── admin/   css/{app,brand}.css · js/{app.js,bootstrap.js,Pages,components,layouts,lib}
│            views/app.blade.php · metronic/ (the licensed theme source — gitignored, see below)
└── site/    css/{site,forms}.css + css/site/{tokens,fonts,icons,base,components,sections}.css
             js/{site.js, site/*, components/forms, lib/forms}
             views/{layout, partials, pages, forms, sitemap}
```
- **The public site is server-rendered Blade with an OPTIONAL locale prefix, and its absence is NEVER a redirect.** `routes/web.php` defines the site routes once in a `$site` closure and registers it TWICE: `prefix('{locale}')->name('web.site.')` first, then unprefixed as `web.site.root.`. So `/contact` serves the default language directly and `/ar/contact` serves Arabic — nothing bounces, and a shared link opens the page it names. **Do NOT collapse that to one group with `prefix('{locale?}')`** — Laravel compiles an optional parameter as a trailing-optional segment, so inside a prefix it stays effectively required and every unprefixed URL 404s. The form routes keep their existing `/forms/{locale}/{slug}` URIs and were NOT moved.
- **Three things make the optional prefix work, and removing any one breaks the site quietly.** (1) `Route::pattern('locale', '[a-z]{2}')` in `RouteServiceProvider::boot()` BEFORE `$this->routes()` — without it `{locale}` swallows any single segment, so `/articles` is read as the locale `articles` and every unprefixed page 404s; and a pattern registered after is missing from a `route:cache` build entirely. (2) `SetLocale` filling in `Language::defaultCode()` when the segment is absent, narrowing to the ENABLED codes (404 otherwise), and setting the Carbon locale. (3) `URL::defaults(['locale' => …])` for EVERY locale INCLUDING the default — a site route cannot be BUILT without a value, so skipping it 500s every default-language page with "Missing required parameter". Keeping `/en` out of the generated URL is a separate, later job: `SiteServiceProvider::hideDefaultLocaleFromUrls()` strips it in `UrlGenerator::format()`.
- **`SiteServiceProvider::hideDefaultLocaleFromUrls()` is what makes the double registration coherent.** A `URL::formatPathUsing` hook strips a leading `/{default}` from every generated path, so the canonical, the hreflang set, the sitemap and every link all say `/contact` while `route(…, ['locale' => 'ar'])` still says `/ar/contact`. Without it a visitor reading `/contact` would click a menu built by `route()` and be thrown back into `/en/…`. It only ever strips a whole first segment, so `/admin/…` and `/forms/en/…` are untouched, and `asset()` does not pass through `format()` at all. `/en/contact` survives as an alias whose canonical points at `/contact`, which is what stops the two being duplicate content. **Site controllers therefore take no `$locale` argument** — the unprefixed routes have no such parameter; read `$this->site()->locale`. `Seo::alternates()` maps a `web.site.root.*` name back to its prefixed twin, and the language switcher reads that same map so it and the hreflang tags cannot disagree.
- **Cost of registering the prefixed group first:** a Page whose slug is exactly two lowercase letters is unreachable unprefixed — `/hr` is read as a locale, fails the enabled-codes check and 404s. It is still reachable at `/en/hr`.
- **`app/Services/Site/` is ONE class — `SiteContext` — and it holds the GLOBAL half of a request only.** Chrome, languages, settings, menus: things every page needs and no page owns. Its whole public surface is getters — `language()` (which is where `locale()`, `direction()` and `isRtl()` all come from, because a Language row already carries the code and `is_rtl`), `languages()`, `defaultLanguage()`, `setting()`, `menuItems()`, `contacts()`, `analytics()`, `url()` — plus the `LINK_ROUTES` map. Nothing else may go back in: **a page's own data belongs to its controller**.
- **THE SEO BUILDER IS GONE FROM `SiteContext`, and putting one back is the mistake this shape exists to prevent.** `seo()`, `meta()`, `breadcrumbs()`, `structuredData()`, `canonical()`, `alternates()` and a private `translated()` reader all lived on it, which meant answering "what does this page put in its `<title>`?" started in a controller, passed through a MUTABLE builder on a singleton, and finished in a partial — three files for one question, and a view (`pages/error`, `forms/*`) could mutate it after the layout had begun. Each controller now assembles a plain `$seo` array and a plain `$breadcrumbs` array and hands both to `view()`. **One method to read per page.** The array's keys are documented on `Web\Site\SiteController`; `site::layout` is the only reader.
- **What is the SAME on every page lives in the LAYOUT, not in twenty controllers:** the ` — Saud International Schools` title suffix (skipped when the title already IS the site name), `strip_tags` + 160-char trim on the description, the crest as the `og:image` fallback, and `x-default`. A controller states its page's own title, description, image, canonical, robots, type and alternates — and nothing about how they are dressed.
- **No JSON-LD.** `structuredData()`, the `EducationalOrganization` node and the `BreadcrumbList` graph were removed with the builder; `partials/content/breadcrumb` reads the controller's `$breadcrumbs` directly and prepends Home itself, so no controller can forget it or spell it differently. `GET /sitemap.xml` is one document with `xhtml:link` alternates; `GET /robots.txt` is a ROUTE and `public/robots.txt` was deleted, because the web server serves `public/` first and would have made the route dead code. The sitemap owns its own `SLUG_ROUTES` map (system page slug → the fixed route that renders it) because it is the only thing that needs one.
- **Site views get ONE ambient variable, `$site`**, from a closure composer on `site::*` in `App\Providers\SiteServiceProvider`. NO global helper. Registering it as a container singleton IS the per-request memoisation — no static state, no `Cache::` layer. It lazily loads settings (one query for the catalogue) and contact details (one query). **Menus are addressed BY CODE — `menuItems('footer_primary')` — with no slot map in between**, one query per menu, memoised by code, whole two-level tree eager-loaded; a page pays only for the menus it renders, so the seeded-but-unused `footer_secondary` is never loaded. Items come back with **`$item->url` ALREADY RESOLVED** — the linked morph wins over the typed external `url`, and null means render an unlinked label. There is no `menuUrl()` to call afterwards, and an unknown code returns an empty collection. `url()` survives as the one morph→route resolver (banners and `$page->menu` use it) and returns null rather than throwing: a menu is chrome and must never 500 a page.
- **The name, the marks and the placeholder are written out where they are used**, not read off `$site`: `@lang('common.site_title')`, `asset('assets/site/images/logo-full.png')` (header), `logo-mark.png` (footer, dividers, og:image), `favicon.png`, `placeholder.png`. One school, one set of marks — a getter that returns a constant is a getter that hides one.
- **Settings expose ONE method, `setting($path)`, returning the stored value.** `settingModel()`/`settingModels()` are gone: a `model` setting stores a bare id and the caller loads what it wants (`Program::find($site->setting('homepage.pathway_program'))`), which is clearer than a generic resolver that had to read `config/settings.php` to work out the class first.
- **The public 404 is `site::pages.error`, deliberately NOT in an `errors/` directory.** Laravel's `RegisterErrorViewPaths` maps every `config('view.paths')` entry plus `/errors` into the `errors` namespace, so a file there answers `errors::404` for the ADMIN and the API too with no way to opt out. `App\Exceptions\Handler::renderHttpException()` renders it by name for site requests only; `admin/*` and `api/*` keep Laravel's own page.
- **The public site is a PORT, not a redesign — match `old/` unless there is a reason not to.** Two rules the home page exists to demonstrate: SECTION HEADINGS RENDER UNCONDITIONALLY (only the content inside a section is `@if`-ed, so an empty news list still says "Latest news" and still offers its CTA rather than the section vanishing), and the home page carries NO article-style body block — the `home` Page row supplies the title and meta description through `$seo` and nothing else. Hero is a swiper of banners with video support and a `btn btn-on-dark` CTA (transparent, white border, fills on hover); a solid `.btn` on hero artwork reads as a foreign object.
- **The form renderer's stylesheet is `site/css/forms.css` and it is ONE FILE.** It used to be two — a neutral token-free `forms.css` plus a `site/forms-theme.css` repainting it — justified by the same component rendering in the admin builder's preview, which has no site tokens. That preview no longer exists and nothing under `resources/admin` imports the sheet, so the split declared every control twice (`.sisf .sisf-input` existing purely to out-specify `.sisf-input`) to serve zero consumers. **IT MUST STAY UNLAYERED.** An unlayered rule beats a layered one whatever the specificity, so wrapping it in `@layer components` (the first attempt) let it win only where nothing else declared anything — every control kept its browser look. It is also **Tailwind-free** with its own scoped reset, because it mounts into markup it does not control and preflight is not guaranteed around it. Colours go through a `--sisf-*` indirection on `.sisf`, which is the retheming surface an admin's Custom CSS overrides. **`--sisf-primary-sweep` is NOT a tint** — it is `--color-brand-soft` (`#3c70a3`), a mid blue that only ever carries white text; anything staying dark-on-light while highlighting uses `--sisf-primary-tint` (`#c6e6fd`) instead, or the thing being emphasised becomes the least readable element on the page. Also note a button element is `.sisf-el--button > .sisf-control > button`: `justify-content` on the outer row computes fine and does nothing, because its single child already fills it.
- **`.sisf-choice*` belongs to radio/checkbox/consent rows; the apply chooser is `.sisf-apply-*`.** The chooser was written as `.sisf-choice` and redefined the same name 400 lines below its original — `display:grid` at equal specificity, later block wins — so every option row on every public form was silently laid out as a two-column grid. Latent only because no seeded form has a radio, checkbox or consent field yet. The chooser also has to carry its OWN `<div class="sisf">`: it mounts straight into `[data-sisf-root]`, which `form-embed.blade.php` deliberately leaves unclassed because `FormRenderer` emits its own root — so without the wrapper every `--sisf-*` in the block was invalid-at-computed-value-time and `border: 2px dashed var(--sisf-border-strong)` computed to `border-style: none`. Safe because the gate is unmounted before the renderer mounts, so the two `.sisf` roots never nest.
- **`disclosure.js` announces every open/close as a bubbling `site:disclosure` CustomEvent** on the panel, with `detail.open`, dispatched from `setExpanded()` — the single place classes and ARIA are written, and after they are written, so a listener reading the DOM sees the state the event describes. It stays generic; `forms.js` is what knows the panel means a form. **That event is what makes cancel-then-apply re-offer the chooser**: the collapse only hides the subtree, so re-opening would otherwise reveal the already-mounted `FormRenderer` and the gate would be a one-time thing. `forms.js` keeps ONE `mounted` handle and every mount goes through `clear()` (unmount + disconnect the phone-field observer), so a rapid toggle cannot stack renderers. **The reset is skipped for a returning visitor** — `config.returning` is set when a rejected submission is repopulating `old()`, and resetting would throw away everything they typed. `telemetry.attach()` is NOT idempotent (it appends listeners and starts a second heartbeat), so it runs once per page load behind a flag; its listeners are delegated off the Blade-owned root that outlives every mount, and telemetry deliberately keeps measuring across a reset because it is the same visitor, token and draft row.
- **THE APPLY PANEL DECIDES ITS OWN OPEN STATE SERVER-SIDE, and it has to.** The submit is a native POST, so everything it has to say arrives as a FRESH PAGE LOAD — and a panel that always started closed hid it: a successful application returned the visitor to an apparently unchanged page, and a rejected one sealed their answers and every field error behind a button reading "Apply now", which reads as "nothing happened". `pages/jobs/show.blade.php` therefore renders `aria-expanded` / `.is-open` / `aria-hidden` from the request itself. Decided in Blade rather than after mount for two reasons: it works with JavaScript off, and it avoids a flash of hidden content. Three details are load-bearing. `.is-open` is `height: auto`, so a panel rendered open is full height with no JS while `setCollapsed()` still measures `scrollHeight` when it is first closed, so the animation survives. `$rejected` is spelled exactly as the renderer spells `returning` (`old('fields', []) !== []`), so the panel cannot open while the chooser is being re-offered nor stay shut while it is skipped. And **`FormRenderer`'s scroll-to-first-error was a no-op** inside a `height:0;overflow:hidden` panel — opening it server-side is what switches that on. On a CONFIRMED submission the toggle is not rendered at all: one application per posting is enforced at submit, so offering to re-open the form is a dead end and an "Apply now" button over somebody's own confirmation contradicts it.
- **The rendered phone field gets intl-tel-input from `site/forms.js`, not from the component.** `PhoneControl` renders a bare `<input type="tel">` on purpose — it also runs in the admin preview, where ~90 kB of country metadata is dead weight. The site already pays that cost for its own Blade phone fields, so `attachPhoneWidget()` adds the selector after mount and re-dispatches `input` on `countrychange` (picking a country rewrites the value without firing one). `components.css` already targets `.iti input.iti__tel-input`, a class the plugin adds itself, so the control inherits the site's existing phone treatment for free. Enhancement only: with the plugin blocked the field still works, and `PhoneType::store()` normalises to E164 server-side regardless.
- **Repeatable groups: a `group` element owns CHILD FIELDS, and the answer stays ONE flat key.** `form_fields.parent_form_field_id` (nullable self-FK) makes a child a real `form_fields` row, so it keeps the builder card, the registry's settings/validation schema and `mergeTranslations` for free — packing children into the group's `settings` JSON would have forked all four. The stored answer is a list of objects under the group's own key (`data['education'] = [{institution, degree}, …]`), so `form_submissions.data` is still a `key => value` map with one entry per TOP-LEVEL capturing field and no reader downstream has to learn about parentage. Rules compile through the existing keyed-suffix mechanism — `GroupType::rules()` returns `.*.institution` and `SubmissionValidator` writes `fields.<key><suffix>` unchanged — which is why the validator needed no special case. **The submit path walks `topLevelFields`, never `fields`**: a child compiled as a phantom `fields.<child>` would be validated twice and stored as a top-level key the form never asked. `SubmissionValidator::withoutBlankInstances()` drops rows the visitor added and never filled, because `GroupType::store()` already discards them and a required child would otherwise reject a submission over a row about to be thrown away — and it PRESERVES ARRAY KEYS rather than reindexing, since the remaining indices are what error messages are keyed by and what the renderer scrolls to. Storage reindexes instead; it has no DOM to line up with. One level only (`FieldTypeRegistry::childCodes()` bars a group and any action from being a child): nesting would make the answer a list of lists, which neither the flat map nor the `''`/`'.*'` contract can express. `is_unique` is refused on a child. Five consumers had to learn the shape — validation, the **webhook payload** (now nested, a real change for existing receivers), the submission drawer (`snapshot()` gained a nested `children` map so relabelling cannot retitle history), the **CSV** (ONE column per group flattened by `GroupType::display()`, because exploding into `education_1_institution…` makes column count depend on the widest row and two exports stop lining up), and `attachFiles()`, which must recurse or a file uploaded inside a repeat is left unattached and still claimable by the next visitor in that session. Add/remove wording is generic — `forms.group_{add,remove,item}` interpolated with the group's own translated label — so adding a group to a form needs no translation work.
- **A COMPLETED SUBMISSION IS WHERE FORMS STOP AND A DOMAIN STARTS, and the seam is ONE lookup.** `config('forms.projectors')` maps a form slug to an `App\Contracts\Forms\SubmissionProjector`, resolved in `ProcessFormSubmission::project()`. Everything before that point is domain-blind: `SubmitController` runs its twelve gates and writes a `FormSubmission`, and nothing in the forms module knows what any form is *for*. **A second domain — a visit reservation, an event booking — is a class and a config line**, reusing the captcha, honeypot, IP/country blocks, per-visitor caps, builder-rendered multi-step fields, scanned uploads and 9 locales without touching forms at all. Three guarantees hold for every projector: only `completed` submissions reach one (spam, drafts and validation failures never do — the fake-confirmation path deliberately writes a `spam` row), a throw is logged rather than fatal (the answers are already stored; losing the notification and webhook too would be worse), and **it must be idempotent**, because re-running is what makes a failed projection repairable and a mapping change fixable over old rows. It runs BEFORE notify/deliver so a notification has a row to link to.
- **HR / recruitment is the first consumer of that seam.** The application is a seeded `is_system` form (`config('jobs.form')` — read by the seeder and the site; the *wiring* lives in `forms.projectors`). `App\Services\Jobs\ApplicationProjector` turns a completed submission into typed rows: `Candidate` (the person) + `candidate_{educations,experiences,languages,skills}` + `JobApplication` (one act of applying). The raw answers stay on the FormSubmission and the application points back at it, so projection is re-runnable; a `spam`/`abandoned`/`validation_failed` row never becomes a person. **`config/jobs.php` is the whole seam** — form answer key → domain column, one file, a constant rather than a mapping UI precisely because the form is `is_system` and cannot drift. The projector is **idempotent**: candidates match on email OR phone (E164, as `PhoneType::store()` wrote it), applications on `unique(job_offer_id, candidate_id)`, and profile children are **replaced wholesale** because a repeat row has no stable id to diff against. `applied_at` is `??=` so a re-run cannot make an old application look new.
- **The general posting is a SEEDED `is_system` row, not a nullable `job_offer_id`.** MySQL treats every NULL in a unique index as distinct, so a nullable column would silently disable dedup for exactly the spontaneous applications most likely to be duplicated. Seeded, it also gets `/jobs/general-application` for free. `is_system` on `job_offers` carries the same contract as on Page and Form: no delete, frozen slug.
- **ONE SCORING TABLE.** `candidate_matches` holds `(candidate × job_offer) => score + comment` for **every** pair evaluated, applied or merely recommended — the candidate drawer reads it one way, the posting drawer the other, and an application shows the same number the recommendation engine produced. `JobApplication::match()` is **a METHOD, not a relation**: the row is identified by two columns and Eloquent has no composite-key relation — `hasOne(...)->whereColumn(…, 'job_applications.job_offer_id')` compiles but throws "Unknown column" because the parent table is not in the subquery's scope, and constraining with `$this->job_offer_id` breaks eager loading. It reads `candidateMatches` when eager-loaded.
- **`app/Ai/` is a CLASS PER PROMPT plus one `Runner`, and every prompt returns declared JSON.** `Prompt` gives `system()`/`user()`/`schema()`/`options()` (temperature 0 — a scorer that drifts between runs cannot be compared across candidates); `Runner` states the shape in the message, tolerates the ```json fence models still add, and **CHECKS the decoded result against `schema()`** so a missing or wrong-typed field throws instead of writing a null nobody notices. That last part is the fix for the previous app's whole failure mode: it asked for prose and scraped the score with a regex the prompt never requested, so it usually stored null. Transport is the existing `Services\Integrations\Ai` on the admin's chosen provider — nothing in `app/Ai/` knows which.
- **THE SCHOOL HIRES FAR MORE THAN TEACHERS, and the scorer is role-aware because of it.** Leadership and admin, nurses and counsellors, IT and finance, drivers, security, catering, cleaning, maintenance. The prompt makes the model identify the role family FIRST, then apply that family's standards — marking a cleaner down for having no IB experience is a wrong answer, and for support and operations roles it says outright that **formal education is largely irrelevant and its absence must not reduce the score**. The same reasoning made the application form's `education` group optional with no minimum row: demanding a qualification before someone can apply for a manual post turns the form into a filter nobody intended. This also inverts the Saudization weighting — support, administrative and operational roles carry far heavier quotas than teaching (some fully reserved), so nationality legitimately moves the score there and barely moves it for a teaching post.
- **The scorer judges WORK AUTHORISATION, not nationality, and that is a correctness choice not a political one.** Ranking Saudi → region → rest scores worse, because nationality is a proxy for two things the model can look at directly: whether the role carries a Saudization quota (profession-specific across hundreds of roles, so a school can be compliant overall and in breach in one department, and losing compliance costs the right to sponsor visas at all), and whether the candidate can start without a new visa. A Riyadh-resident teacher with a transferable permit beats someone nearer by needing fresh sponsorship. The prompt also carries the market's real signals — IB/British/American curriculum experience, subject or education degree, home-country registration, and employment gaps as *a question to ask*, not a disqualification. The candidate is described from the TYPED tables, facts only and no name, so two applications worded differently cannot score differently for that reason.
- **`ScoreCandidateMatches` is one job PER CANDIDATE, never in the request.** It scores against open postings, narrowed to shared clusters *once the candidate has any* — a brand-new candidate has none, and scoring them against everything is right then, because at the volume where that hurts, clusters exist. A single posting's failure `continue`s rather than failing the job, so one refusal cannot cost the scores that already succeeded or trigger a retry that re-scores them all. The score is **clamped** 0–100: the schema guarantees a number, not that the model respected the range. Dispatched from the projector via `DB::afterCommit` — on a sync queue it would otherwise read rows the transaction has not written.
- **Embeddings are a SEPARATE driver capability, `App\Contracts\Integrations\GeneratesEmbeddings`.** Not folded into `GeneratesText`: a provider can chat without embedding and vice versa, and `Ai::resolve()` now takes the capability it needs so asking an unequipped integration to embed fails with a message that says so. `OpenAiDriver::embed()` is batched (a rebuild embeds hundreds at once), asks for `dimensions: 256` because MySQL has no vector type and cosine runs in PHP, and **sorts the response by `index`** — the API may return out of order and a silently mismatched vector would make every cluster wrong while nothing looked broken. **Verified live against a real key** (integration "Jobs test"): one call returns 256 real floats. That matters because until the blank-`Ai` fix below, embeddings could never have worked at all, so this path had never once run against the provider.
- **Reading a FILE is a third driver capability, `App\Contracts\Integrations\ReadsDocuments`** — beside `GeneratesText` and `GeneratesEmbeddings`, for the same reason those two are apart. It is `readableTypes()` + `read()`, and `readableTypes()` is part of the contract rather than a convenience: a form collects more formats than a provider reads, so a caller must be able to ask BEFORE spending a round trip on a refusal. **`OpenAiDriver::read()` posts to `/v1/responses`, NOT to the `/v1/chat/completions` that `generate()`/`chat()` use, and that is what makes a Word CV readable at all** — Chat Completions takes a file part but only a PDF (`Expected file type to be a supported format: .pdf but got .docx`), while the Responses API is where the `.doc/.docx/.rtf/.odt` support lives. The shapes are NOT interchangeable: `input` instead of `messages`, an array of content parts instead of a string, `input_text`/`input_file` instead of `text`/`file`, `filename`/`file_data` at the part's own level instead of nested under `file`, `text.format` instead of `response_format`, `system` spelled `developer`, and the answer at `output[]` → the item whose `type` is `message` → its `output_text` parts, never `choices.0.message.content`. Read the message item BY TYPE: a reasoning model puts `reasoning` items in front of it, so `output.0` works until the day the configured model reasons and then silently returns ''. (There was a window where `/v1/responses` listed those types and rejected them anyway — a provider-side bug fixed in March 2026. If Word CVs start failing again, read `integrations-*.log` before assuming the driver is wrong.) The file goes **inline as base64, never through the Files API**: an upload leaves a second copy of somebody's CV on the provider's storage with its own lifetime, and nothing in this app would ever delete it.
- **`Runner::check()` re-encodes a structured answer instead of blanking it, and that is load-bearing.** `ParseCv` declares its three repeatable sections as `string` meaning *a JSON array encoded as a string*, and a model asked for that will sometimes send the array itself — being more structured than it was asked to be, not wrong. The old `is_scalar($value) ? … : ''` turned that into `''`, `CvParser` decoded `''` to null, dropped the key, and the applicant saw **every repeatable section empty** with no exception and no log line — indistinguishable from a CV that listed no jobs, and the exact failure class `Runner` exists to prevent. An array is now JSON-encoded back into the string the schema asked for; only a value that is genuinely neither throws.
- **The CV parser resolves nationality to an ISO code before it reaches the renderer.** The form field is a select over `countries.code`, so a free-text answer selects nothing: `SelectControl` matches on `value`, the applicant sees an untouched required dropdown, and the FIRST SUBMIT fails with "the selected nationality is invalid" against a field that looks empty — only on the AI path, so nobody would reproduce it. `ParseCv` now asks for the alpha-2 code, and `CvParser::country()` is the net: it matches the answer against the code, the translated demonym and the translated country name in **every** locale (a CV in Arabic says `سعودي`), and **drops an unresolvable answer** rather than passing it through, because a blank the applicant fills in costs five seconds and a rejected submit does not.
- **`FieldData` carries `min`/`max`/`step`, and both generated halves read them.** Without them a `type: 'number'` field rendered `<input type="number">` with no step — so the browser default of 1 made `0.7` invalid HTML in a field that exists to hold decimals — while `Registry::fieldRules()` added only `numeric`, so `5` passed validation and the provider rejected it at call time far from the form that accepted it. `step` accepts the string `'any'` because that is the word the browser itself spells and no number substitutes for it (0 invalidates everything, omitting it means 1). Bounds are gated on `type === 'number'` at BOTH ends, so a `min` on a text field is ignored rather than silently becoming a length rule. Declared today on `temperature` and `score_threshold` (0–1, `'any'`) and on the SMTP `port` (1–65535, step **1** — the one place stepping is deliberate). **The admin form renders from `integration_drivers.schema`, a DB column mirrored at seed time**, so a schema change needs `php artisan db:seed --class=IntegrationDriversSeeder` before the constrained input appears; server validation picks it up immediately from the live class. Note `app/Services/Forms/FieldTypeRegistry::fieldRules()` is a SECOND, independent rules builder over the same `FieldData` and does not read these — a forms field-type declaring a bound would render it and not enforce it.
- **`Media::getPathAttribute()` must read `$this->getAttributes()['folder']`, never `$this->folder`.** The model has both a `folder` COLUMN and a static `folder()` helper. On a row straight out of `Media::create()` that did not assign the column — `create()` keeps only what it was given — the attribute is absent from the bag, so Eloquent's `__get` falls through to relationship resolution, finds `folder()`, gets a string and throws **"App\Models\Media::folder must return a relationship instance"**. A model re-loaded from the database carries the column and works, so the failure appears only on a freshly created row and the message points nowhere near the cause.
- **NEVER type-hint `Ai` as an optional `handle()` parameter on a queued job.** `EmbedCandidate`/`EmbedJobOffer` took `?Ai $ai = null` as a test seam and it was never null: Laravel resolves `handle()`'s dependencies through the container, `Ai` is constructible, and its `?Integration $integration` auto-wires to a BLANK model — so `resolve()` skipped its honest "No AI integration is configured." and threw `Registry::driver(): Argument #1 ($code) must be of type string, null given` out of `Integration::resolveDriver()`. The wrapper's `try` logged it rather than failing the job, which is why it sat in `integrations-*.log` looking like a config problem. The real damage is the case that never happened yet: the blank object would have **shadowed `Ai::default()` once a provider WAS configured**, so embeddings could never have worked. Both jobs now call `Ai::default()` directly; that IS the seam, and nothing can inject past it. **`Runner` had the SAME bug and an earlier revision of this file wrongly said it did not** — its `__construct(protected ?Ai $ai = null)` was a promoted constructor parameter, and the container fills those exactly as it fills `handle()`'s, so `app(Runner::class)` came back holding a blank `Ai` that shadowed `Ai::default()` for all three AI jobs and the CV parser. Nullable-with-a-default does not mean "left null": it means "resolved if resolvable". `Runner` now takes no constructor argument and exposes `using(Ai $ai)` for a caller that genuinely wants to pin one. `?Runner`/`Runner $runner` hints remain fine — it is `Ai` that must never be injected.
- **`Vectors` is k-means in PHP, and its SEEDING is the load-bearing part.** Deterministic seeding is required (cluster identity must survive a rebuild), but taking "the first k vectors" is broken here: callers order by ULID, which is creation order, and candidates arrive in WAVES — a batch of teachers, then a batch of cleaners. The first k are then near-identical, the centroids start on top of each other and never separate, and everyone lands in one giant pool. That is not hypothetical; it is what the first version did. `seeds()` uses **farthest-point (deterministic k-means++)**: no randomness, so two rebuilds of unchanged data still agree exactly, but the seeds are spread across the space. Verified: three synthetic families of 12 split 12/12/12, identically across runs.
- **`RebuildClusters` runs nightly at 03:00 and CARRIES IDENTITY ACROSS REBUILDS.** Each new centroid is matched to the nearest previous cluster (greedy, so one previous pool cannot be claimed twice) and reuses that row above a deliberately low 0.6 similarity — orphaning a drifted pool is worse than reusing it. A locked cluster keeps its hand-written name. Below `Cluster::MIN_CANDIDATES` it stands down entirely and matching falls back to every open posting. Postings are placed by cosine against the same centroids — **one shared embedding space**, so there is no second taxonomy to keep in step.
- **Clusters are EMERGENT, and they exist to bound the match matrix.** Not seeded: a nightly rebuild k-means over `candidates.embedding` (JSON, **256 dims** — MySQL has no vector type, so cosine runs in PHP) and an LLM names each result; `is_locked` protects a hand-titled one, and identity is carried across rebuilds by matching new centroids to the nearest old one or every saved filter silently repoints. Below `Cluster::MIN_CANDIDATES` clustering is noise and matching falls back to all open postings. Without clusters, 500 candidates × 30 postings is 15,000 LLM calls. **`CandidateMatch`, `CandidateCluster` and `JobOfferCluster` are deliberately UNOBSERVED** — all three are written in bulk by the queues, so an observer would add thousands of audit rows a night recording that a machine did its job (the same reasoning that keeps `Session` out of the log); what a *person* does to a pool is audited on `Cluster`.
- **Job notifications are emitted from `JobApplicationObserver`, and the status one is gated on `wasChanged('status')`.** Without that gate a re-projection — idempotent and routine — would announce "status changed" every time the projector re-read a CV. `created()` carries the new-application notice, so a re-projection of an EXISTING application never announces it twice. Both are wrapped: an integration being down must not roll back the status change or throw out of an observer. Note an application form also fires `form.submission_received` because it IS a form; the two `job.*` types carry the posting and the applicant, so HR subscribes to those and whoever watches forms generally is not drowned. **Observer overrides must take `Model $model`** — narrowing the parameter to `JobApplication` is a fatal PHP signature clash with `BaseObserver`.
- **VISITS is the SECOND consumer of the projector seam, and it added nothing to the forms module.** Two lines in `config/forms.php` (`submission_rules` + `projectors`) and a `config/visits.php` twin of `config/jobs.php`. `App\Services\Visits\ReservationProjector` turns a completed `visit-reservation` submission into `Visitor` (the household) + `VisitReservation` (one act of booking) + `VisitAttendee` (the children). Same shapes as jobs: `Visitor` ≈ `Candidate`, `VisitReservation` ≈ `JobApplication`, `VisitAttendee` ≈ `CandidateEducation`. `VisitSlot` has no jobs analogue.
- **A SLOT'S LIMIT COUNTS RESERVATIONS, NOT PEOPLE, and the two numbers bound different things.** `visit_slots.capacity` is how many BOOKINGS a time accepts; `visit_services.max_visitors` caps how many people one booking may bring, and it is the ceiling of the party-size counter on the card AND of the `students` group at submit. Collapsing them makes one meaningless. **Only a CANCELLED reservation gives its seat back** (`VisitReservation::scopeActive`) — a no-show still occupied it on the day. `VisitSlot::state()` is the ONE place `open|limited|full|closed` is decided, so the public calendar, its legend, the admin grid and the feed cannot disagree; `limited` finally emits `.fc-event.is-limited`, which the stylesheet had carried since the site was written and nothing ever used. It is BOOKABLE — the old rule styling it `not-allowed` was corrected when something started emitting it.
- **`unique(visit_slot_id, visitor_id)` is the dedup AND the projector's idempotency key.** One index does both jobs, and neither column is nullable for the reason `job_applications` documents. "Block the same phone or email on the same slot" is true rather than merely "the same email" because `Visitor::scopeIdentifiedBy` matches on email **OR** phone, exactly as `Candidate` does — `VisitReservationIsAllowed` looks the household up that way before the index ever sees them, so the common case is a sentence under the email input instead of a constraint violation.
- **THE OVERBOOKING GAP IS LEFT OPEN ON PURPOSE.** The submit-time rule checks capacity inside the request; the projector runs after the response, so two people can take the last seat in between. The projector locks the slot, re-counts, and when it finds it over capacity **still writes the reservation** — the visitor has already been shown a confirmation, and silently voiding a booking somebody believes they hold is worse — then logs `visits.slot-overbooked` to the `integrations` channel. The admin calendar renders `reserved/capacity` and rings an over-capacity slot so a person resolves it.
- **The visits page is ONE URL and THREE STEPS, one on screen at a time.** `/visits` renders the card grid server-side (readable with no JS, indexable) plus two more sections — a card holding the calendar, and a card holding the form — and `site/visits.js` moves between them by toggling `hidden`, which takes the inactive steps out of the tab order rather than merely out of sight. **WHICH STEP THE PAGE OPENS ON IS DECIDED IN BLADE**, because the submit is a native POST and a rejected one arrives as a fresh page load: `$rejected` (spelled exactly as `FormPresenter` spells `returning`) opens it on step three with the card header filled from the same `old()`, and the form itself opens on the page carrying the errors. `site/visits.js` is the gate: pick a visit → mount `VisitSlots.svelte` → pick a time → mount `FormRenderer` **with `values`**, the same seam the CV chooser uses. It cannot be presets: the jobs page knows its posting server-side, this page does not. That is also why `site::partials.forms.embed` grew a `$marker` flag — leaving `data-sisf` on would have `site/forms.js` mount a SECOND renderer into the same root. Changing the time remounts with the answers read back out of the renderer's own hidden mirrors, so a half-filled form survives it.
- **`ReservationProjector` computes the headcount BEFORE the first save.** Writing the reservation and then correcting `visitors_count` produced a second audit row on every booking saying nothing but "1 became 2", and left the `created` row claiming a party of one. `attendeeRows()` maps and filters, then the count and the row are written together and `writeAttendees()` inserts. The stored count is the number of children actually listed — the hidden `visitors_count` answer is the ceiling the visitor picked, enforced as a max and never stored.
- **Slot ids must come from the MODEL'S generator, not `Str::ulid()`.** The bulk generator and the demo seeder both write with `insertOrIgnore`, which bypasses Eloquent — and `HasUlids` lowercases what the helper returns, so reaching for it made those the only uppercase ids in the database. `(new VisitSlot)->newUniqueId()`.
- **Visit permissions are PER TRANSITION too** (`visit-reservations.{contact,confirm,attend,no-show,cancel,reopen}`): a school wants a receptionist who can confirm without being able to cancel, and someone marking the register on the day who does neither. One action per TARGET status, so `lib/visitReservation.js` mirrors the state machine the same way `lib/jobApplication.js` does. Note the 422 wording picks its own article — jobs hardcodes "A" and gets away with it because none of its statuses begins with a vowel; `attended` does.
- **FACILITIES is the THIRD consumer of the projector seam, and the first to reuse another module's table.** The venues the school rents out — hall, labs, sports complex. `config/facilities.php` twins `config/visits.php`, two lines go in `config/forms.php`, and `App\Services\Facilities\ReservationProjector` turns a completed `facility-reservation` submission into a `FacilityReservation`. **The person is a `visitors` ROW, shared with visits** — matched on email OR phone, so a family that books a school tour in September and the hall in November is one contact record and the desk sees both. That is why `Visitor` has `visitReservations()` and `facilityReservations()` rather than a bare `reservations()`: an unqualified name would silently mean "visits only" to a reader of the facilities code. Verified live — a booking made with a *different email but the same phone* as an existing visit booking reused the row.
- **THE SLOT ENGINE IS A DELIBERATE CLONE, not an abstraction.** `facility_slots`/`facility_reservations` and their controllers, drawers and admin calendar are copies of the visits ones. The trade was taken with eyes open: ~1,000 duplicated lines, and a slot bug to fix in two places, bought against refactoring a module that had shipped and been verified days earlier. The ONE thing shared is `resources/site/js/site/islands/SlotPicker.svelte` (renamed from `VisitSlots.svelte`), because it takes `slotsUrl`, `labels`, `selectedId` and `onselect` and knows nothing about either domain — so sharing it cost one import line and avoided a second copy of the calendar.
- **A FACILITY HAS THREE URLS, AND THAT IS WHAT KEEPS THE BUILD CHEAP.** `/facilities/{slug}` describes it, `/facilities/{slug}/contact` carries the contact form, `/facilities/{slug}/reserve` carries the booking wizard. ONE FORM PER PAGE, because `partials/forms/renderer.blade.php` emits `id="sisf-schema"`/`id="sisf-config"` as literals and `site/forms.js` does `querySelector('[data-sisf-root]')` — singular. Two forms on one page would have needed the forms module generalised, **including keying `old('fields')` and the error bag per form** (both are global today, so a rejected booking would have repopulated the contact form with the booking's answers). Splitting the URLs avoids all of it: nothing under `app/Services/Forms/`, `SubmitController` or `site/forms.js` was touched. The dividend is visible on the contact page, which has **no page-specific JavaScript at all** — the venue is a server-side preset and the standard `data-sisf` marker mounts it exactly as `/inquiries` does.
- **Articles and albums are ATTACHED to a facility, never owned by it.** `facility_articles`/`facility_albums` are first-class pivots with their own ULID keys, managed by `PivotDrawer` in its bulk shape. The article keeps its own URL and its own listing; detaching changes nothing about it. The old module inverted this with a nullable `facility_id` ON the articles table, so an article belonged to one venue OR to the main site and every main-site query had to remember a `->main()` scope it could silently forget. Both pivots log in **pivot mode** against the FACILITY (`isPivot()`, `parent()`, `related()`), so the audit row reads "Added :name to the facility" with the article's name in `meta`.
- **A venue booking has NO party size and NO attendees** — the brief is a name, an email and a phone, and a slot's limit already counts bookings. That is the one place the facilities shape is genuinely smaller than the visits one, and it is why `components/visits/VisitorProfile.svelte` takes `attendees = null` meaning "this kind of booking names nobody" (distinct from an empty array, which a school visit passes and which is worth showing) plus a `personLabel` prop — the same row is a *guardian* to visits and *whoever booked* to facilities.
- **The facility contact form has NO projector, deliberately.** A message is a message: it stays a `FormSubmission` read under Forms → Submissions. The stated cost is that those cannot be filtered per venue there, because the facility id lives in the answer JSON. Adding it later is a class and one line in `config('forms.projectors')`.
- **`VisitAttendee` is DELIBERATELY UNOBSERVED**, for the reason `CandidateMatch` is: the projector replaces those rows wholesale on every projection, so an observer would record a delete and an insert per child every time a booking was re-read. `VisitSlot` IS observed — the bulk generator writes with `insertOrIgnore` and fires no events, so what lands in the log is only the deliberate acts a person takes afterwards.
- **NEWSLETTERS ARE THE FOURTH CONSUMER OF THE PROJECTOR SEAM, and the first whose OPTIONS ARE LIVE DATA.** `/newsletters` carries the mailing-list signup as a seeded `is_system` builder form (`config('newsletter.form')` = `newsletter-subscribe`), posted to the unchanged `/forms/{locale}/{slug}` endpoint and turned into `newsletter_group_subscribers` rows by `App\Services\Newsletter\SubscriptionProjector` — so it inherits the honeypot, the minimum submit time, the **captcha**, the country and IP blocks, the per-visitor caps, nine locales and one submission pipeline to export and notify from. It was briefly a bespoke Blade POST for one reason — a form's choices are `form_field_options` rows written once at seed time, so a list an admin adds next week would never be offered and posting its code would fail the `Rule::in` the option rows themselves define — and that reason is now answered by a sync rather than by forking the module.
- **`App\Services\Newsletter\FormOptions` IS WHAT MAKES A BUILDER FORM SAFE OVER LIVE DATA.** `options()` is the read model (a group as a form choice); the seeder calls it once through `options_from => 'newsletter_groups'`, and `NewsletterGroupObserver` keeps it in step afterwards. **ON THE OBSERVER, NOT IN THE CONTROLLER** — the controller is one of several ways a group is written and the seeder is another. Two things it must keep doing: upsert on `(form_field_id, value)`, which is the table's unique index, and **never leave the field with zero options** (`UpdateBuilderData::declaredRules()` requires `min:1` and the renderer would draw an unanswerable control). Note a reseed cannot repair the options — `FormsSeeder::run()` builds structure only for a form it just created — so this sync is the only writer after install.
- **THE SYNC HANGS OFF `saved()`, NOT `created()`/`updated()`, AND THAT IS A BUG FIX NOT A PREFERENCE.** Eloquent fires `created`/`updated` inside `performInsert()`/`performUpdate()` and `saved` only later in `finishSave()` — while `NewsletterGroupObserver::saved()` is where the one-default invariant is enforced, with a builder update that fires no events. Syncing from the earlier hooks therefore ran while TWO rows still carried `is_default`, and `FormOptions::options()` sorts default-first: the tie fell through to `name`, the option order was written for a two-default world, and nothing re-synced afterwards. Promoting a list left the OLD default sitting first in the public checkbox list until some unrelated edit happened to recompute it. Reproduced and fixed. The one thing still in `updated()` is the `code` rename, which must run BEFORE the sync — the only place that event ordering helps rather than hurts.
- **THE OPTION VALUE IS THE GROUP'S `code`, NOT ITS ULID, and `rename()` is the price of that.** Whatever sits in `value` is verbatim what lands in `form_submissions.data`, and nothing resolves it back: none of select/checkbox/radio overrides `display()`, so `BaseFieldType` implodes raw values into the CSV, the submission drawer and the notification summary — ULIDs there are unreadable, and they would make every audit row this sync writes a wall of them. The cost is that `code` is admin-editable, so `NewsletterGroupObserver::updated()` moves the option's value on a rename (reading `getOriginal('code')`) before syncing; without that a rename reads as one list retired and another appearing.
- **CHECKBOXES, NOT `<select multiple>`.** Both capture several values — a select needs `settings.is_multiple`, spelled exactly that, and a field seeded with `multiple` silently renders a single-value dropdown — but a native multi-select needs ctrl-click to add a second choice and collapses to a scrolling box on a phone. This is the **first seeded form in the app with a `checkbox` field**, so `.sisf-choices` / `.sisf-choice` / `.sisf-choice-label` in `site/css/forms.css` had never been exercised until now. Related: `min_selected`/`max_selected` live in `form_fields.validation`, not in `settings`, and a multi-select has no `validations()` at all — `is_required` is what gives `required|array` here.
- **`min_submit_seconds` IS SET TO 2 ON THIS FORM, AND HAD TO BE.** NULL does not mean "no minimum": `Form::minSubmitSeconds()` falls back to `config('forms.spam.min_seconds')`, which is 5. This form is two fields, a returning visitor with autofill beats five seconds, and tripping that rule is **silent** — a fake confirmation and a `spam` row — so the visitor would believe they had subscribed and would not have. `FormsSeeder::guards()` is what lets a definition say so; before it, `run()`'s `firstOrCreate` passed no spam or captcha column at all. The number is a literal in the definition and NOT a config key — one was added and removed again, because `run()` only writes on create and the column is admin-editable afterwards, so a config value could never take effect on any install that already had the form and would just be a second number to drift.
- **CAPTCHA NEEDS BOTH COLUMNS AND AN INTEGRATION ROW.** `Captcha::forForm()` returns no challenge unless `is_captcha_enabled` AND `captcha_integration_id` are set, and `enabled()` further wants a resolvable driver plus a filled `site_key` and `secret_key` — so a form flagged on with nothing pinned is silently **unprotected**, not broken. There is no `IntegrationsSeeder` and no env key (the keys live in `integrations.config`), so `FormsSeeder::guards()` resolves the oldest enabled captcha integration at seed time and leaves the column null when an install has none: on a fresh install an admin must create the reCAPTCHA integration and pin it. Fail modes are asymmetric — a MISSING secret fails open, a WRONG one fails closed on every submission, and a provider outage fails open by design.
- **THE PROJECTOR'S IDEMPOTENCY IS DATED, NOT FLAGGED, and that is the subtle part.** The obvious "set `is_active = true`" is wrong twice: re-running an old submission would silently un-unsubscribe somebody who has since left, and never touching an existing row would break the one documented way back onto a list. So the write is gated on the SUBMISSION'S timestamp — a row is (re)activated only when its `subscribed_at` is earlier than that instant, and is stamped with it rather than with `now()`. **The instant is `submitted_at`, NOT `created_at`**: the telemetry beacon force-flushes `start` on the visitor's FIRST INTERACTION and it is that send which CREATES the draft row, which `SubmitController::newSubmission()` later claims — so `created_at` can be up to `config('forms.token_ttl')` (two hours) before they actually subscribed. Reading it stored the wrong moment for an admin to read, and refused reactivation to anyone submitting from a tab older than their last signup. Re-running writes nothing; somebody who unsubscribed afterwards stays off however often it is re-run; a genuine re-signup is a newer submission and reactivates. One signup writes one row PER LIST CHOSEN, because the unique index is `(newsletter_group_id, email)`.
- **AN ADDRESS ALREADY ON THE LIST IS TOLD "SUCCESS", and moving to the forms module made that free.** There is deliberately NO entry in `config('forms.submission_rules')` for this form: a rule answering "already subscribed" would tell anyone who asks whether a given address is on the list, which is the same fact `NewsletterController::unsubscribe()` refuses to leak by answering a bogus signature and a real one identically. Because projection runs after the response, every submitter sees the same confirmation regardless.
- **THE SIGNUP SITS ABOVE THE ARCHIVE, AND THAT IS ABOUT WHERE THE CONFIRMATION LANDS.** `SubmitController::confirmation()` returns the visitor with `back(303, [], formPageUrl(...))`, and a `back()` destination comes from the Referer, which never carries a fragment — so the visitor lands at the top of the page and the confirmation renders wherever the embed sits. Below the archive table it is off-screen, which is exactly how the bespoke version managed to say nothing at all after a successful signup (its flash was above the archive while the redirect's `#newsletter-subscribe` scrolled past it, and `data-auto-dismiss` deleted it after 5s regardless). **A new system form must also be added to `SiteContext::SYSTEM_FORM_ROUTES`** or `formPageUrl()` returns `url('/')`, which has no embed partial, and the confirmation is set and silently dropped. The residual limit is shared with `/contact`: a full-viewport hero still sits above the card, so the confirmation is below the fold on landing until `confirmation()` learns to carry a fragment.
- **The unsubscribe stays bespoke, and it is the one thing this page still says itself.** It is not a submission — a GET arriving from an inbox carrying a signature, with no form behind it — so it keeps its own route, which runs `set.locale` because the URI has no locale segment and building the `/newsletters` URL to return to would otherwise throw "Missing required parameter". `web.site.newsletter-groups.unsubscribe` is a FROZEN name (`NewsletterGroupSubscriber::unsubscribeUrl()` builds every recipient's link from it and `ShipNewsletter` has already posted those links). Its message is flashed under `NewsletterController::NOTICE` and rendered by the page directly rather than through `site::partials.ui.flash`, because that partial carries `data-auto-dismiss` and `disclosure.js` deletes anything wearing it after five seconds — right for a transient flash, wrong for the one confirmation somebody gets that they have left a list.
- **TWO THINGS ABOUT THE PAGE ARE LOAD-BEARING AND LOOK LIKE STYLING.** The anchor div carries `scroll-mt-24`: this is the app's ONLY `withFragment()`, and `.site-header` goes `position: fixed` at 88px (`--header-height-scrolled`) the moment the page is scrolled at all — which a fragment jump does — so without a scroll margin the unsubscribe confirmation lands entirely behind the navbar (`--spacing` is 5px here, so 24 is 120px). And the intro paragraph is inside `@if ($presentation)`: the embed is a three-way branch, and unconditionally the paragraph told a visitor to "choose a list and enter your email address" directly above their own confirmation that they had, printing the unsubscribe sentence twice running.
- **THE NEWSLETTER SIGNUP IS THE FIRST SEEDED FORM WITH A `checkbox` FIELD AND THE FIRST WITH CAPTCHA INSIDE A `.card`.** Both were latent surfaces. `forms.css` styled no invalid state for a choice group at all — section 5's rules name only `.sisf-input`/`.sisf-select`/`.sisf-textarea` — so a rejected required checkbox group rendered its ticks untouched with only the red error text below; `CheckboxControl` also needed `role="group"` for its `aria-invalid`/`aria-describedby` to mean anything on a bare `<div>`. Both fixed. STILL OPEN: a reCAPTCHA **v2** widget is 304px wide and `.card { overflow: hidden }` + `.card-body { padding: 40px }` clips it below ~375px — not currently reachable because the pinned integration is v3, which renders no visible widget, but it becomes real the day somebody switches.
- **`php artisan translations:forget {group} {key*}` IS THE REMOVAL PATH, and `TranslationService::remove()` is what it drives.** Adding a key was "add it to `catalogue()`, reseed"; removing one had no path at all — dropping the entry removes nothing from an install that has already seeded, because `putMany()` only ever writes, so a retired key kept resolving through `__()` on every existing install while a fresh one no longer had it. The command does both halves (`--dry-run` first) and says out loud that the catalogue edit is a third place; `lang/` is generated and gitignored, so a deploy carries the catalogue edit but not the files. `remove()` deletes the lines under one lock and prunes any parent left empty (`export()` renders an empty array as `[]`, so a leftover parent makes `__()` return an array and `@lang` print "Array"). **The `translation_keys` row is the caller's job and must go too**: with `fill_missing_keys` false nothing notices a stale row today, but flip it true and the next admin edit to any key in that group re-inserts the removed one as `''` in every locale — and `''` is present, so the fallback never fires and every locale renders a blank. The signup's own wording is NOT in the catalogue: a builder form's title, labels, placeholder and confirmation are `locale => string` maps on the seeded row, and only `site.newsletters.{panel,subscribe.intro,unsubscribed}` remain as page copy.
- **The group select offers EVERY group, because `newsletter_groups` has no `is_public` flag.** A list an admin does not want offered publicly cannot currently say so; adding that is a column, a Data-class field, an admin input and a `where` in `FormOptions::options()`.
- **Job permissions are PER TRANSITION** (`job-applications.{shortlist,contact,call,hire,reject}`), not one `update`: a school wants a screener who can shortlist but not reject, and a manager who can hire without touching the queue. `candidates.cv` is separate from `candidates.show` because the CV is personal data behind a signed link and triaging a list should not require pulling files.
- **`App\Contracts\Forms\SubmissionRule` + `config('forms.submission_rules')` is the hook for checks a FIELD cannot make** — "has this person already applied to this posting?", "is that posting still open?" — because they read two answers together or another table. Providers return rules keyed by the usual `fields.<key>` path and `SubmissionValidator::make()` **merges** them onto what the element already declared (never replaces, or `email:rfc` would be wiped). Returning a rule rather than aborting is what puts the message under the input the visitor can fix, instead of letting the submission succeed and the projection fail silently behind it.
- **FIELD KEYS ARE UNIQUE PER FORM, GROUP CHILDREN INCLUDED — two groups cannot both name a child `start_year`.** The DB enforces `unique(form_id, key)` and it is load-bearing: `SubmitController::upload()` resolves a file field BY KEY ALONE, so two groups' `certificate` children would be indistinguishable. Relaxing it to `unique(form_id, parent_form_field_id, key)` does not work — MySQL treats every NULL as distinct, so top-level fields would lose uniqueness entirely (the same NULL trap as the general posting). The seeded application form therefore uses `from_year`/`to_year` and `responsibilities` in experience against `start_year`/`end_year` and `achievements` in education, and `config/jobs.php` maps them back to the shared columns — **that is what the map is for**. `FormsSeeder::assertKeysUnique()` catches a clash before the first row is written, because otherwise it surfaces as a bare PDO "Duplicate entry" from inside a half-built form that `firstOrCreate` will never repair — the form has to be deleted and reseeded.
- **THE UPLOAD SESSION SURVIVES A REJECTED SUBMIT, and it did not used to.** `SubmissionToken::mint()` minted a fresh `sid` on every render, and `PublicFormUpload` refuses media whose `form_session` is not the one in the current token — so any validation failure ORPHANED every file already uploaded and the visitor was told to attach their CV again. Invisible until now only because `contact` and `inquiries` have no file fields. `FormPresenter::present()` now decrypts `old('submission_token')` and reuses its `sid` when it is the visitor's own, still valid, and for this same form; anything else mints fresh, so the binding is preserved without being widened.
- **The `job-application` form is seeded, `is_system`, and NOT reachable at `/forms/{slug}`** — `FormsController::show()` 404s system forms by design, so it is rendered by the job page rather than served directly. **5 pages / 35 keys** (22 top-level + 13 group children): details+CV, education, experience, languages, skills. **ONE SECTION PER PAGE, which is what retired two of the three separators** — a page that is titled "Work experience" does not also need a caption saying so, and `SeparatorType`'s own docblock says a separator is not a heading. The one left (`sep_cv`) is UNCAPTIONED and splits the personal fields from the CV, the only break a page boundary no longer makes: the field below it is already labelled "Curriculum vitae", so a caption would print the same words twice running — the failure that made `FormRenderer` stop printing the form's own title above its first input. Nationality's 249 options are generated from the `countries` table via `options_from`, because writing them into config in nine languages would treble the file to restate a table the app already has.
- **The `visit-reservation` form is seeded, `is_system`, and NOT reachable at `/forms/{slug}`** — same as its job sibling: `FormsController::show()` 404s system forms, so the visits page renders it. **2 pages / 15 keys** (11 top-level + 4 group children). Page 1 "Your details": the three hidden fields carrying what the wizard chose, then the four guardian fields. Page 2 "Who is coming": the `students` group of first/last/grade/current school. Split because the two are different questions asked about different people, and because the group GROWS — five children is twenty inputs, so a shared page's length would be set by the party size rather than by the form. **None of the three hidden fields is `is_required`**, deliberately: an empty slot id would otherwise be reported as "The visit slot id field is required", naming an input the visitor cannot see, where the rule answers the same case with a sentence about time slots. The student keys are PREFIXED (`student_first_name`) because field keys are unique per form including group children, and `config/visits.php` maps them back onto the shared columns — that is what the map is for. The 15 grade options are `FormsSeeder::gradeOptions()`, shared with `inquiries` so the two forms cannot disagree about what a year is called.
- **`CandidateEducation` pins `$table` explicitly.** Laravel's inflector treats "education" as UNCOUNTABLE and infers `candidate_education`; the table stays plural like its four siblings, and without the pin it fails at runtime with "table doesn't exist" rather than anywhere a reader would look.
- **ONE php-directive form per Blade file — never both the inline and the block form.** Blade's `storePhpBlocks` matches the opening directive through the first closing one across the WHOLE file, and it runs BEFORE comments are stripped. An inline directive above a block one pairs with the BLOCK's terminator and swallows everything between, compiling to a syntax error pointing at an unrelated later line — and writing the directives literally inside a Blade comment is enough to trigger it on its own. `partials/ui/pagination.blade.php` + `partials/layout/analytics.blade.php` carry the note.
- **The admin is the Inertia+Svelte+Metronic app. The site is the public website end users visit.** Nothing under `site/` may import from `admin/`, or the whole Metronic theme lands on a public page. The two have no shared module: the form renderer under `site/js/components/forms` is site-only, and the admin builder keeps its own copies of the two helpers it needs (`admin/js/lib/forms/{values,i18n}.js`) rather than reaching across.
- **Aliases:** `@` → `resources/admin/js` (so every existing admin import is untouched), `@site` → `resources/site/js`. An `@site/` import inside `resources/admin` is a boundary violation you can grep for.
- **Separate builds, separate manifests.** `npm run build` = `build:admin` then `build:site`; each is `vite build --mode {admin,site}` and writes to `public/build/{admin,site}`. A Vite build emits exactly one `manifest.json`, so the two cannot share a directory — hence the second argument in `@vite([...], 'build/admin')` / `@vite([...], 'build/site')`. A bare `vite build` with no `--mode` throws rather than silently half-building. `npm run dev` still serves BOTH from one server (Laravel keys hot mode off a single `public/hot` and ignores the build directory while it exists, so two dev servers cannot coexist).
- **Blade is namespaced `admin::` / `site::`** (`AppServiceProvider::registerViewNamespaces()`, both paths also in `config/view.php`). Inertia's `$rootView` is `admin::app`; the public form pages are `site::forms.*`. Use the prefix in our own code so a name that exists on both sides can never resolve to the wrong half.
- **Tailwind: both stylesheets use `@import 'tailwindcss' source(none)` + explicit `@source`.** v4's automatic source detection scans the WHOLE project and ignores `@source`, so without this the public page compiled every utility class found in `resources/admin` (site CSS was 37 kB; it is 11 kB scoped). Each side scans `../js/**/*.{svelte,js}` **and `../views/**/*.blade.php`** — the Blade shell's `<body>` class list is Tailwind utilities too, and dropping that glob strips the demo1 layout off the page.
- **`public/` mirrors the split:** `public/assets/admin/media/**` (Metronic's app/audio/avatars/brand-logos/flags/images) and `public/assets/site/` for the site's own static files. `public/build/` is Vite output, gitignored.
- Admin `lib/` — `api/{client,useIndex.svelte,useForm.svelte}`, `date`, `format`, `permissions`, `upload`, `activity`, `kt` (KTUI init), `menu` (sidebar config), `portal`, `toast`, `confirm`.
- Admin `components/{ui,form,data,media,feedback,layout,activity,charts,forms-builder}` — the deduplicated kit. Key: `IndexCard` (Metronic list card + fly-in create/edit swap), `DataTable` (sortable, skeleton, `kt-table`), `Filters` (config-driven drawer incl. `resource-select`), `Drawer`/`Modal` (Svelte-driven, portaled), `Dropdown` (portaled — avoids table overflow clipping), `Select` (async combobox = Select2 replacement), `PhoneInput` (intl-tel-input), `PasswordInput`, `DatePicker` (flatpickr), `MediaPicker`/`MediaLibraryModal`.
- Admin `layouts/{AdminLayout,AuthLayout}`, `Pages/Admin/**` (the `Admin/` segment is kept: it is the Inertia page key that `inertia('Admin/Users/Index')` passes) + `Pages/Admin/Auth/Login`.
- Note `components/form/` (admin input kit) and `site/js/components/forms/` (public renderer) are different things — before the split they sat side by side, distinguished only by a plural `s`.

- **ANALYTICS IS ONE INSERT-ONLY TABLE PLUS ONE ENDPOINT, and it is deliberately shallow.** Google Analytics is already wired as a browser tag (`Analytics::default()->client()`, emitted by `site::partials.layout.analytics`) and carries the deep reporting; `site_page_views` exists so the numbers a school looks at daily are on the page it lands on. **ONE ROW PER PAGE VIEW, written by `App\Http\Middleware\RecordPageView` and nothing else.** No visit row to find, no idle window, no read-modify-write, and therefore no concurrency to reason about — which is the whole reason it is per page rather than per session. It is NOT telemetry: no scroll depth, no focus order, no beacon, and **no new JavaScript on the public site at all**. `count(*)` is page views, `count(distinct visit_key)` is visits and `count(distinct visitor_key)` is visitors, so three metrics come off one scan with no extra storage. `MassPrunable` at 365 days on the daily `model:prune` (auto-discovered — no bespoke command, nothing to register), and **UNOBSERVED**, for the reason `AppServiceProvider` already gives for bulk machine-written tables: an observer would write an audit row per page view.
- **THE NAMING IS `SitePageView` / `App\Services\Analytics\` BECAUSE EVERY OBVIOUS NAME WAS TAKEN.** `Visitor`, `visitors`, `VisitSlot`, `VisitReservation`, `VisitAttendee`, `config/visits.php`, `App\Services\Visits\`, `visits.*` and `MorphType::Visitor` all belong to the school-tour booking module, where a `Visitor` is a *household*. Never introduce a bare `Visit`, `Visitor` or `visits.*` here.
- **A PAGE'S IDENTITY IS ITS ROUTE NAME PLUS SLUG, NEVER ITS PATH — and `RouteName::normalise()` is why the reports are not split nine ways.** `routes/web.php` registers the site twice, so `/contact`, `/en/contact` and `/ar/contact` are one page under two route names (`web.site.contact` and `web.site.root.contact`). The middleware normalises before it stores and `DashboardMetrics` normalises `SiteContext::LINK_ROUTES` before it joins — **the same helper on both sides**, because two copies of that regex would silently stop matching the day one changed and the symptom would be an empty top-content table rather than an error. `path` is stored for a human reading one row and nothing ever groups on it.
- **TOP CONTENT RESOLVES TITLES BY INVERTING `SiteContext::LINK_ROUTES`, so there is no second map to maintain.** That constant already maps a `MorphType` alias to its route name for menu links; inverted, it turns `articles.show` into `App\Models\Article` via `MorphType::classFor()`, and one `whereIn('slug', …)` per type decorates the top ten. Adding a content type to the site therefore makes it appear here for free. All ten of those models carry a translatable `title`, so no per-type column map is needed. **Public links must be built from the `web.site.root.*` name**: `route('web.site.articles.show', …)` THROWS "Missing required parameter" from an API request, because `SetLocale` never runs on `/api` and `URL::defaults(['locale' => …])` is unset — the unprefixed registration exists precisely because it has no `{locale}`.
- **THE SKIP RULES ARE THE MODULE, and `status !== 200` is the load-bearing one.** `pages.show` is a `{slug}` catch-all, so `/wp-login.php`, `/.env` and every mistyped link MATCH a real site route and reach the middleware — and the 404 renders `site::pages.error` as **`text/html`**, so the content-type rule would not have caught them. Without the status rule the most-read table fills with pages that never existed. The content-type rule is what drops `visits.slots` and `facilities.slots` (JSON calendar feeds inside the site group) without naming them; prefetch is refused across all four header generations (`Sec-Purpose` *containing* `prefetch`/`prerender`, `Purpose`, `X-Purpose`, `X-Moz`) because Chrome prefetches on hover and would otherwise make the navigation's targets the busiest pages. Bots are RECORDED with `is_bot`, excluded from every query, and surfaced as one footnote number.
- **The work happens in `terminate()`, and the middleware keeps NO instance state.** Two of the skip rules need the response, and under FPM `terminate()` runs after `fastcgi_finish_request()` so the insert costs the visitor nothing. `Kernel::terminateMiddleware()` calls `$this->app->make($name)`, so **the object that ran `handle()` is not the one that runs `terminate()`** — a property set on the way in is gone on the way out. `handle()` is a bare pass-through and everything is read from `$request`/`$response`, which is what makes that harmless; if state ever has to cross, use `$request->attributes`, never a property.
- **`visit_key` HMACs the session id and is NEVER the raw value** — that id is the cookie, i.e. a credential, which is why `Session::$hidden` hides it and routes bind on the ULID. Same construction as `SubmissionGuard::hashIp()`, so the app has one recipe. `visitor_key` is an ip+user-agent HMAC with **no rotating salt**, deliberately: a daily salt would make `count(distinct …)` mean *visitor-days* and turn the tile into a plausible lie over any range longer than a day. Its honest limit is the proxy itself — it under-counts a computer lab behind one NAT and over-counts anyone moving from Wi-Fi to cellular, which is why the tile says "approximate". Both columns are `$hidden`.
- **`UserAgentParser` and `GeoResolver` MOVED to `App\Services\Analytics\`, and `SubmissionContext::entryPoint()` was extracted into `Acquisition`.** They never had any forms coupling, and the traffic module would otherwise have imported from a module it has nothing to do with. **Dependency direction is forms → analytics, never back.** Four files broke with no `use` line to grep for — `SubmissionContext` (twice), `SubmissionGuard` and `FormPresenter` resolved both classes by same-namespace lookup — so sweep with `grep -rn "GeoResolver\|UserAgentParser" app/`, not a `use`-based grep. `Acquisition` holds the only search-engine and social-host lists in the app; `Acquisition::host()` normalises the referrer host AT WRITE TIME, which is why the dashboard's referrer query is a plain `GROUP BY` rather than `SubmissionAnalytics::referrers()`'s nested `substring_index` chain.
- **GEO IS A CHAIN — CDN header → local `.mmdb` → null — AND SHARING IT CHANGED FORMS BEHAVIOUR ON PURPOSE.** The header stays gated on `isFromTrustedProxy()` because a header is spoofable; the database needs no gate because it reads `$request->ip()`, which nothing a client sends can move. `FormBlockedCountriesController` shares this resolver, so **country blocking on a site with no CDN goes from failing open for everyone to actually blocking** once the database is installed — correct, arguably a bug fix, but tell the admin before installing it. `isConfigured()` is now `isFromTrustedProxy() || reader() !== null`. Everything fails open to null and nothing throws, or a missing file would take every public form offline. The `Reader` is memoised on a **static**, because `GeoResolver` is injected into four separate constructors and an instance property would open the file up to four times per request. Private and reserved ranges are rejected before the file is opened — **which is why the Countries card is always empty in development**, where every request is `127.0.0.1`; do not "fix" that by deleting the guard.
- **The database is `maxmind-db/reader` + DB-IP Lite, not `geoip2/geoip2` + GeoLite2.** The reader is pure PHP with zero runtime dependencies and reads either vendor's `.mmdb`, so which vendor supplies the data is a config value rather than a code change; `geoip2/geoip2` would drag in Guzzle for a web service this app never calls. DB-IP needs no account and no licence key, so `analytics:geoip-update` works on a fresh clone with an empty `.env` — the difference between geo working and geo silently returning null forever. It is CC-BY-4.0, and the attribution is the "IP geolocation by DB-IP" line in the dashboard footnote. The command month-stamps its URL and **falls back to the previous month on a 404** (DB-IP publishes on the 1st, so a run at 00:05 races it), and it **verifies `8.8.8.8` resolves to `US` before swapping the file in** — a truncated download otherwise installs cleanly and returns null forever, indistinguishable from "nobody visited from abroad", and on an install behind Cloudflare that check is the only thing that ever exercises the reader at all. Not bundled: 40 MB does not belong in git, so running it once is a deployment step.
- **THE DASHBOARD IS TWO HALVES IN ONE CALL, and the activity half adds NO storage.** `GET analytics/dashboard` returns traffic (from `site_page_views`) and activity — four `GROUP BY status` queries over `form_submissions`, `job_applications`, `visit_reservations` and `facility_reservations`, tables that already exist. All four use spatie/model-states, which stores the state's own `$name` in a plain `status` column, so grouping on it raw is correct and no state object is instantiated. Each ranges on the date that means "when this happened" for its own domain (`created_at`, `applied_at`, `booked_at`). **Every activity section is gated SERVER-SIDE, per domain**: a caller without `job-applications.index` gets no `applications` key at all, not an empty one and not a hidden one, so the hiring pipeline never reaches a browser that may not see it. `analytics.index` gates the data; `dashboards.index` still gates the page, so an editor reaches their landing page without necessarily reading the school's numbers — and with the permission absent the Svelte page returns before its `lastKey` compare and fires **no request**, rather than eating a 403 toast on the first screen after signing in.
- **NO DONUTS AND NO MULTI-COLOUR CATEGORICAL CHARTS on the dashboard.** `lib/charts.js` ships FOUR validated categorical slots and states they are assigned in order and never cycled; entry points has six buckets and countries ten, so either would have to invent colours outside the validated set — a palette change, and out of scope. Every breakdown is a single-colour horizontal bar with `legend: { show: false }` and identity carried by the axis label, exactly as the forms page already does. The one multi-series chart is the timeline (two series, two slots). The KPI tile moved out of `Forms/Analytics.svelte` into `components/ui/StatTile.svelte` when the dashboard became its second consumer, and the forms page's `{#snippet tile(...)}` now just renders it so its call sites are unchanged. The dashboard defaults to **30 days, not all time** — deliberately different from the form page, which is opened to ask "how is this form doing overall" rather than "how are we doing now".
- **THIS DASHBOARD WILL NOT MATCH GOOGLE ANALYTICS, AND WILL READ HIGHER.** GA's bot filtering is a client-side JS gate most scrapers never execute; ours is a user-agent substring match, so a scraper wearing a Chrome UA counts as a human. That is the module's accuracy floor and the reason GA stays wired — the footnote says so on screen, which is what stops it being filed as a bug and what stops the next person growing this into GA.

## Conventions (match these)
- **Svelte 5 runes only** — `$props/$state/$derived/$effect`, callback props, snippets. No `export let`/`createEventDispatcher`/`on:`.
- Preserve the **Metronic demo1 look** (`kt-*` classes). Icons = **keenicons** (`ki-filled ki-*`).
- A module Index = `AdminLayout` + `IndexCard` with `toolbar`/`form`/`table` snippets; create/edit = **fly-in card swap**; view/filters/pivots = **right-side drawers**; row actions = portaled `Dropdown`.
- UI strings are plain English literals in the component — no translation layer, no lang files.
- **Phone inputs are normalized before validation.** A Data class with phone fields does `use App\Traits\Data\NormalizesPhones;` and names them in `phoneFields()` (defaults to `['phone']`). It hooks spatie/laravel-data's `prepareForPipeline()`, which runs BEFORE every pipe — so `Rule::unique` and `App\Rules\PhoneNumber` see E164 (`+213555123456`) and `+213 555 123 456` collides with an existing row instead of becoming a second account. `App\Services\Phone\PhoneFormatter::e164()` is the one formatter; it returns null for anything unparseable, and the trait falls back to the raw input so the validator reports it rather than `nullable` silently storing no phone.
- **Models are banner-sectioned** — every model in `app/Models/` has exactly four numbered sections, always all four in this order even when empty: `1. Attributes` (consts, `$guarded`, `$hidden`, `$appends`, `$casts`) → `2. Relationships` → `3. Accessors` (`get*Attribute()`) → `4. Methods` (everything else). Don't invent domain sections (Lifecycle, Permissions, …) — fold them into these. Format:

## Gotchas (already solved — don't reintroduce)
- npm `@keenthemes/ktui` has **no `KTMenu`** → sidebar accordion/collapse are **Svelte-driven**, not `data-kt-menu`. KTUI (dropdowns/toggle/sticky/theme-switch) is init via `lib/kt.js` `initKt()` in `app.js` + `AdminLayout`.
- **Keenicons** must be imported in `app.js` (unlayered), NOT `@import`-ed into `app.css`, or Tailwind's `::before` reset wipes the glyphs.
- Don't put `kt-drawer` on the Svelte `Drawer` (its base CSS mis-positions it). `#app` needs `flex-grow:1;width:100%` (in `app.css`).
- KTUI widgets in client-rendered content (form panels, drawers) won't be re-init'd → use Svelte-native equivalents (`PasswordInput`, portaled `Dropdown`).
- **Flat media storage: never delete a media's *directory*, only its file.** The folder is shared by every model — a `deleteDirectory()` there wipes the whole app (this is what medialibrary's `DefaultFileRemover` and the old `ScanUpload` both did). Same reason `file_name` is a ULID with a unique index: two `invoice.pdf`s would otherwise be the same file.
- **Observers write the audit log; don't call `activity()` from controllers.** A model `updated` diff must ignore timestamps and skip empty diffs, or every password change writes a meaningless row.
- `useIndex` reads its `filter` **once at init** → a drawer reused across rows needs `setFilters()` on open (and `readUrl:false`, or it fights the page's query string).
- `Filters` passes `value=` (not `bind:value`) to `Select` and relies on `onchange`. A `resource-select` may take function props of the draft + `dependsOn` (see the causer filter in `Pages/Admin/Activities/Index.svelte`).
- PHP here is **8.1** — no constants in traits, no `readonly` classes.

## Legacy import — `php artisan legacy:import`

**ONE COMMAND MOVES THE OLD APP IN, AND IT IS SAFE TO RUN AGAIN.** `legacy:import --legacy=<old-db> --files=<old storage/app/public>` is the whole deployment step: restore the old dump into a database, put the old uploads somewhere readable, run it, read the report. Everything reconciles through a `legacy_imports` table (legacy integer id → the ULID row it became), so a second run reports **0 created, 0 updated** — which is what makes "run it, fix a mapping in `config/legacy.php`, run it again" the normal way to use it. The map is also the only thing that can identify a row with no natural key (a grade is a *name inside a programme*, a menu item a *name inside a menu*, a slot two datetimes), and `prune()` drops mappings whose target an admin has since deleted so it is re-importable rather than skipped forever. The table is a record of a migration, not application state — droppable once the import is verified.
- **`config/legacy.php` IS THE MAPPING SURFACE, and nothing else is.** Every place the two schemas disagree about a NAME lives there: menu name → frozen menu `code`, legacy class → this app's class, legacy enum → this one's, a legacy settings row → a setting *or* a contact-detail row, a legacy table → the system form its rows are submissions of, and the `dropped` list of columns with no destination. Straight column-to-column copies are NOT there — an importer spells its own columns out, so reading it tells you what it writes without a second file open.
- **`files` RUNS FIRST AND FILE NAMES ARE PRESERVED — that one decision is what makes a decade of rich-text content portable.** Both apps store uploads flat and serve them at `/storage/uploads/`; the old one as `uploads/{uuid}.{ext}`, this one as `uploads/{ulid}.{ext}`. Copied across under its own name, a legacy file keeps the exact URL it had, so every `<img src="/storage/uploads/….jpg">` inside a translated `content` column still resolves with **no HTML parsing and no rewriting**. It costs nothing (`file_name` is unique, and a UUID cannot collide with a ULID). `--strip-host=https://old.example.com` removes an absolute old hostname, leaving the path half — which is already correct. Editor images come across as **free media**, which is what they always were in both apps, and that is also why the module runs first: content importers *attach* a file rather than importing one, and whatever nobody claims stays in the library.
- **CVs MOVE TO THE PRIVATE DISK, which is a fix rather than a port.** `LegacyFiles::TARGETS` maps a legacy owner to an upload target, and `App\Models\JobApplication` → `private:forms`. The old app had one disk, so a CV sat in the same world-readable folder as the home-page hero; carrying that across "because that is where it was" would import the old app's weakest decision along with its data. Imported media is written `clean`, not `pending` — these files were served publicly for years, and routing them through `ScanUpload` would quarantine every image on the site until a worker caught up.
- **THREE OF THIS APP'S STANDING BEHAVIOURS ARE SWITCHED OFF WHILE IT RUNS.** The audit log (`activity()->withoutLogs()`) — observers write a row per model write, and fifty thousand of them would bury every real audit row, the same reasoning that keeps `Session`/`CandidateMatch`/`SitePageView` unobserved. Notifications (`NotificationService::withoutNotifications()`, the one addition outside `App\Services\Legacy`) — `JobApplicationObserver` announces a new application, and importing three thousand would announce three thousand things that happened last year. And the queue, pointed at the `null` driver — `JobOfferObserver` dispatches an embedding on write and the projectors dispatch scoring, so on a sync queue a migration silently spends money. `--with-ai` leaves the queue connected; the better order is to import first and re-embed once the data is known to be right.
- **JOBS AND VISITS ARE WRITTEN DIRECTLY, NOT THROUGH THE PROJECTORS, and the reason is not performance.** The obvious move — synthesise a `FormSubmission` per legacy row and let `ApplicationProjector`/`ReservationProjector` do the rest — is wrong twice: those rows never WERE submissions (a bespoke controller, no token, no telemetry, no answers to store), so the submission would be a fiction invented to satisfy a seam; and a projector dispatches embed + summarise + score per candidate. The importers copy the projectors' **rules** instead — candidate and visitor matched on **email OR phone** through the models' own `identifiedBy` scopes, applications keyed `(posting, candidate)`, bookings keyed `(slot, visitor)`, profile children and attendees **replaced wholesale** because a repeat row has no stable id, and `applied_at`/`booked_at` set with `??=` so a re-run cannot make an old record look new.
- **`contact_submissions` and `inquiries` DO become FormSubmissions, because they always were submissions.** The old app gave each a typed table, which is why adding a third form meant a migration; here they are submissions of the seeded `contact` and `inquiries` system forms and are read under Forms → Submissions. Every row lands `completed` with spam score 0 — scoring old data against today's rules would retroactively hide real enquiries behind a fake confirmation — and the telemetry columns stay **null, never zero**, because `duration_seconds = 0` is the exact signal the spam rules read. The `fields` snapshot is built by the real `SubmissionValidator::snapshot()` so it cannot drift from what the drawer expects.
- **`setJson()` EXISTS BECAUSE MYSQL NORMALISES JSON KEY ORDER.** Eloquent's `isDirty()` compares a JSON column as an *encoded string*, so a value read back from the database and re-encoded in insertion order never matches and the row is dirty on every run forever. The symptom is a re-run reporting "updated" for rows nothing touched — which destroys the one property the whole import is built on. It was reproduced on `form_submissions.data`/`fields` and fixed; same underlying fact as the explicit integer `order` in the submission snapshot.
- **THE RENAME MOST LIKELY TO BE GOT BACKWARDS: the old `newsletters` table is this app's `documents` table.** A legacy "newsletter" was a downloadable PDF — a name, a translated title, a file. This app's `Newsletter` is an email campaign with a subject, groups and a send state; importing the old rows into it would produce a queue of unsent mailings built out of PDF titles. Nothing in the import touches that table, and the mailing-list side correctly starts empty.
- **Other shape changes worth knowing.** `achievement_categories` → the one flat `categories` list (`code` takes the legacy slug). `brand_assets.group`, a bare string column, becomes real `brand_asset_groups` rows in first-seen order. `program_streams` → `streams`, and `programs.has_streams` is dropped because this app asks the table. `job_postings.is_remote` (yes/no) → `work_mode` (`onsite`/`remote`; nothing becomes `hybrid`, because the old data never recorded it). A facility's `articles.facility_id` becomes a `facility_articles` pivot — the inversion this app made deliberately — and everything that made a facility a mini-site (domain, theme, logo, its own contacts, tagline, address) is reported as dropped. `menus` runs EARLY and `menu-items` LAST, because a page carries a `menu_id` while an item can link to anything; that split is the only arrangement with no cycle, and nesting is a **two-pass** write since a child may legitimately have a lower legacy id than its parent.
- **`--phone-region` IS AN EXPLICIT DECISION ABOUT ONE INSTALL'S HISTORY.** `PhoneFormatter::e164()` refuses to guess a region — right for a form somebody is filling in now — so a legacy table full of `05xxxxxxxx` cannot normalise at all, and un-normalised numbers are exactly what makes Candidate and Visitor dedup miss. The option is import-only; without it those numbers are kept verbatim and **counted**, and the run says how many.
- **LEGACY `settings.value` IS JSON-ENCODED, AND THE MULTI-VALUE ROWS ARE ENCODED TWICE.** Found against the real database, not the probe. The old admin `json_encode`d whatever it was given before writing, so `head_code` is stored as `"<!-- Google tag …"` — quotes included — and every URL carries escaped slashes (`https:\/\/…`); `phones` holds the *string* `["(966) 920002877"]`, itself encoded again. Read raw, the Custom Head Code block arrives wrapped in a stray quote pair, every social link is a backslashed string that does not resolve, and `pathway_program_id` comes through as `"4"` which the import map cannot look up. `SettingsImporter::decode()` peels repeatedly, and **the first-character gate is what keeps it safe**: `json_decode('4')` is a valid int, so an unguarded loop would turn the programme id string into an integer and then into nothing. Only a value opening with `"`, `[` or `{` is treated as encoded. `blank()` exists for the same reason — the old table is full of rows written as the JSON string `""`, which a raw emptiness test reads as a value and then reports as an unmapped setting that was never set.
- **THE OLD SLOT TABLES HAD NO UNIQUE INDEX AND THESE DO, so `LegacyImporter::slot()` FOLDS DUPLICATES.** `visit_slots` is unique on (service, starts_at, ends_at) and `facility_slots` on (facility, starts_at, ends_at) — deliberately, since that is what makes the admin's duplicate-slot 422 possible. The legacy tables allowed the same window twice and the real data is full of it: **609 of 3,422 rows**, a complete duplicate set left by a bulk generator that was run a second time over a term. Two legacy rows describing one window ARE one slot here, so the second reconciles onto the first and **both legacy ids map onto that one row** — which is the load-bearing half: a booking made against either legacy slot still resolves, and two bookings that were on separate duplicates land where `unique(slot, visitor)` can see them. Capacity takes the higher claim. `created_at` takes the **earlier of the two, as a min rather than an assignment** — two folded rows carry two timestamps, so assigning makes each rewrite the other on every run and the import reports hundreds of "updated" rows forever, which is exactly the property the design rests on. Separately, a slot whose owner was deleted in the old app (the FK was nullOnDelete — **8 rows** in the real data) is unimportable here, where the column is NOT NULL, and is REPORTED rather than silently skipped, because the per-owner walk would never otherwise see it.
- **`identify()` EXISTS BECAUSE TWO OF THIS APP'S OWN RULES PULL AGAINST EACH OTHER.** `Candidate::scopeIdentifiedBy` and `Visitor::scopeIdentifiedBy` match on EMAIL **OR** PHONE — verified behaviour, and what makes a household one record — while `email` and `phone` are each **UNIQUE** on both tables. Live those coexist, because a collision is one failed request. Replayed over years of history they collide hard: the real data has **40 phone numbers against two or more different email addresses** and 30 addresses against two or more numbers (agencies applying for several people, families sharing a line, typos), so a row matched BY PHONE had its email overwritten with one a DIFFERENT candidate already owned and the import **died on a duplicate-key violation a third of the way through 3,908 rows**. The rule now: an identifying value already on file is never overwritten and one another row owns is never taken — first writer wins, which also removes the churn of two legacy rows rewriting the same column on alternate runs. 154 values were refused on this install and the count is REPORTED, because a refusal means two records sharing a number were merged into one and that may be two different people. **The same latent conflict exists in `ApplicationProjector::candidate()`**, which still `fill()`s email and phone onto a candidate found by either; there it degrades to a logged projection failure rather than a crash, because a throw out of a projector is caught.
- **`earliest()` IS THE GENERAL FORM OF THE `created_at` TRAP, and it bites wherever several legacy rows fold onto one.** Slots folded by window, candidates folded by email-or-phone, applications folded by (posting, candidate), reservations folded by (slot, visitor) — in every case two legacy rows carry two different timestamps, so ASSIGNING lets each rewrite the other on every run and the import reports hundreds of "updated" rows forever. A min converges inside the first run and is stable after it. This is the same class of defect as `setJson()`: something that looks like a cosmetic reporting wobble but is actually the idempotency guarantee failing.
- **NATIONALITY IS FREE TEXT IN THE OLD SCHEMA, so `config('legacy.nationalities')` + Arabic folding do the rest.** Matching on the countries table alone left 10 distinct values unresolved across 33 applications. Three causes, and only two are safe to fix: EXONYM DRIFT (the table says `Türkiye`, applicants wrote `Turkey`), and ARABIC ORTHOGRAPHY AND GENDER (`الأردن`/`الاردن` differ only by a hamza; `سعودية` is the feminine of the stored `سعودي`). `foldName()` normalises alef variants, ta marbuta, alef maqsura, harakat and tatweel on BOTH sides so the comparison is symmetric, and the alias map handles the rest — **down to 2 values on 2 applications**, both genuinely ambiguous (`Filipino Married to Saudi`, `Australia and New Zealand`), which are deliberately left blank because a guess there would never show itself as a guess. The report names every unmatched value with a count, deduplicated — warning per row would print thousands of lines saying the same ten things.
- **THE OLD `forms` TABLE IS NOT A FORM BUILDER — IT IS A LIST OF DOWNLOADS, and this is the rename most likely to be got backwards in the other direction.** Four columns (id, name, timestamps), a translated title and one attached file; on the real install it holds "School Contract 2026-2027", "Grade 3 Summer Pack 2026", "Timetables Grade 6-12 Girls". This app's `forms` is a builder with pages, fields, options, webhooks, spam guards and submissions, plus four seeded `is_system` rows the site resolves BY SLUG — so importing those fifteen rows into it would create fifteen unsubmittable forms and collide with the seeded ones. They are `documents` here, alongside the old `newsletters`, which is why `DocumentsImporter` reads TWO legacy tables and `config('legacy.morphs')` points `App\Models\Form` at Document rather than at null.
- **TWO LEGACY TABLES SHARING ONE DESTINATION IS WHY `LEGACY_SOURCES` IS KEYED ON THE LEGACY CLASS.** It used to map this app's class back to a legacy table, which works right up until `newsletters` and `forms` both become Document: `array_search` can only return one of them, so every menu item pointing at the other would have resolved to the wrong row or to nothing. Keyed on the legacy side the question has one answer.
- **GRADE GUIDELINES ARE INVISIBLE IN THE OLD SCHEMA and were missed on the first pass.** The old app gave them no table and no column — a guideline was a `files` row morphed onto the Grade with `is_main = 0`, and the old Grade model declared no file relation at all, so nothing in `grades` hints that they exist. The only way to find them is to ask which models own files (`SELECT model_type, COUNT(*) FROM files GROUP BY model_type`), which is worth doing on any install before trusting the run. Fifteen of them here, one per grade, now attached to `Grade::GUIDELINES_COLLECTION`.
- **AN IMPORTED CV MUST BE GIVEN AN OWNER OR THE NIGHTLY PRUNE DELETES IT — a data-loss bug found only by importing at scale.** `Media::prunable()` sweeps private-disk media with `model_id IS NULL` older than seven days, and `model:prune` runs daily. Live, a submitted CV is never caught because the file is OWNED by the FormSubmission and `candidates.cv_media_id` is only a pointer at it. This import deliberately writes NO form submission for a job application, so nothing owned the imported CVs and **3,762 of 3,909 were prunable on arrival**, with legacy timestamps years past the threshold: the first nightly prune would have deleted the files and the rows and left `cv_media_id` pointing at nothing. `ApplicationsImporter::claimCv()` now files each one on its candidate under a `cv` collection — every application's CV, not just the newest, because an earlier CV is history rather than rubbish. Written as plain columns, since Candidate does not use `HasMedia` and `UploadService::attach()` calls `singleFileCollections()` on the owner. One row stays unowned on this install, and correctly so: it belongs to a legacy application that no longer exists.

## Build / run
`npm run build` (both bundles; or `npm run build:admin` / `npm run build:site`, or `npm run dev` for one server serving both) + `php artisan serve`. No jQuery. Detailed history + rationale: `~/.claude/plans/audit-the-app-folder-elegant-wreath.md` and the `remake-context-artifacts` memory.

**Dev runs on a DOMAIN, not on `127.0.0.1` — `http://sis.localtest.me:8000`.** reCAPTCHA validates the hostname a token was minted on against the key's registered domains, and an IP literal is not a hostname, so a real key cannot be tested against `127.0.0.1`. `*.localtest.me` is a public DNS zone that resolves to `127.0.0.1`, which buys the domain with **no hosts-file entry and no elevation** — `php artisan serve` binds loopback as usual and the name resolves onto it. Register `localtest.me` in the reCAPTCHA console (the match covers subdomains) and it works; the port is ignored by that check, so 8000 is fine. For a hosts-based `sis.test` instead — offline-proof, no third-party zone — add `127.0.0.1 sis.test` to `C:\Windows\System32\drivers\etc\hosts` as Administrator and change the one `APP_URL` line; `sis.test:8000` is already in the stateful list. Both hosts keep working alongside `127.0.0.1:8000`.
- **`SANCTUM_STATEFUL_DOMAINS` IS SET EXPLICITLY IN `.env`, and it has to be.** The admin authenticates by Sanctum session, so a host absent from that list receives no stateful cookie — the public site works, the login page renders, and every admin API call 401s with nothing to explain it. `config/sanctum.php`'s own fallback could not have covered a new host: it read `sprintf('%s%s', $hardcoded, env('APP_URL'), Sanctum::currentApplicationUrlWithPort())` — two placeholders, three arguments — so the raw APP_URL was glued on without a comma (yielding the entry `::1http://127.0.0.1:8000`, matching no host) and the one call that formats it correctly was dropped as surplus. It worked only because `127.0.0.1:8000` is hardcoded in the string. Fixed to Laravel's own shape, but the env var is what the app actually uses.

**Metronic source is `resources/admin/metronic/`** (5,275 files, ~547 MB) — it belongs to the admin because nothing else may use it. Gitignored via `/resources/admin/metronic`; if you ever move it again, move that `.gitignore` line in the SAME commit or a licensed third-party theme lands in the repo. Only five imports reference it: four `@import '../metronic/src/css/…'` in `admin/css/app.css` (config, components/index, demos/demo1, and `components/fullcalendar.css` — which the theme ships but its own `components/index.css` never imports, so the visit time-slot calendar would otherwise render stock blue-and-grey inside a Metronic card) and the keenicons `styles.bundle.css` in `admin/js/app.js`. It is deliberately NOT covered by the `@source` globs, so Tailwind never scans the theme's own 5,275 files. Because it sits inside `resources/`, a raw `grep -r resources/` in a shell walks all of them and effectively hangs — pass `--exclude-dir=metronic`. The Grep tool is unaffected (ripgrep honours `.gitignore`).
